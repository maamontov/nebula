# План доработки рабочего пути Desktop → аудио → STT → ревью

Дата: 2026-09-10. Основание: повторное ревью commit `c165722`.
Статус: план подготовлен; реализация не начата.

Этот документ уточняет оставшуюся работу из [предыдущего плана](remediation-plan.md). Он не требует заново реализовывать исправленные контракты, скоринг и изоляцию БД. Задача — соединить существующие компоненты и проверить пользовательский сценарий, который не покрывают текущие backend-тесты.

## 1. Подтверждённое исходное состояние

- Tauri запускает захват и сохраняет файлы, но отправителя в `/api/v1/interviews/{id}/audio/chunks` нет. Worker сам локальный spool не импортирует.
- На момент ревью в `apps/desktop/src-tauri/spool` около 2800 файлов; в рабочей БД 0 audio_chunks и 0 TRANSCRIBE_AUDIO jobs. Корневой spool пуст.
- Desktop и backend используют относительный `./spool` из разных рабочих каталогов.
- Stop отправляет пустой список manifests; пустая очередь принимается за завершённую обработку. После 15 секунд UI пытается перейти в review независимо от готовности.
- Отсутствующий аудиовход заменяется default input, а уровни громкости возвращаются константами.
- Оценивание может читать все ревизии и все ответы кандидата при отсутствии привязки к вопросу.
- После перезапуска UI теряет выбранное интервью: состояние хранится только в памяти React.
- 107 Python-тестов проходят. Тест, названный сквозным, вставляет готовую стенограмму через Repository и не проверяет Tauri, доставку аудио и STT.

Число файлов — снимок, не критерий готовности. Существующую запись не останавливали, аудио не прослушивали и провайдерам не отправляли.

## 2. Границы решения

- Использовать существующие Tauri, Rust audio-capture, SQLite, API приёма чанков и PipelineWorker. Не вводить отдельный сервис доставки или второй STT-путь.
- Выбрать один механизм доставки: нативный отправитель в desktop. Не добавлять параллельно backend-watcher тех же файлов.
- Захват сохраняет локальную durable копию, отправитель передаёт завершённые чанки, backend подтверждает durable приём и создаёт STT job. Не выполнять HTTP и файловый обход в аудиоколбэке.
- Принятый чанк, выполненный STT и готовность к ревью — разные состояния. Пустая очередь сама по себе ничего не доказывает.
- Сохранять существующие записи. Не очищать spool и не пересоздавать рабочую БД ради зелёного теста.
- Изменения вести без сабагентов. После каждого этапа обновлять статус и прикладывать фактическую проверку.

## 3. Этапы и зависимости

Порядок: **A → B → C → D → E → F → G**. Сначала инфраструктура доставки, затем корректность завершения и источников, оценивание, восстановление и полная проверка.

### A. Единая конфигурация хранения и сохранность старых записей

Статус: не начат.

Файлы: scripts/nebula.sh, backend API/configuration, Tauri commands/AppState, SetupScreen/API-клиент, audio spool.

1. Определять абсолютный корень данных один раз при запуске. Передавать согласованные пути backend и desktop; убрать `./spool` из SetupScreen.
2. Разделить внутри корня владение файлами: capture spool и backend spool, если существующий приём переписывает файлы/метаданные. Не допускать одновременной записи Rust и Python в один путь. Проверить существующие форматы имён и manifest до выбора подкаталогов.
3. Зафиксировать конфигурационный контракт для dev-запуска и desktop-запуска вне корня репозитория. Недоступный путь должен давать понятную ошибку старта.
4. Инвентаризировать существующий Tauri spool: интервью, дорожки, epoch, sequence, checksum, наличие закрытого manifest. Не читать/выводить содержимое речи в диагностике.
5. Подготовить безопасное восстановление старых записей: использовать те же ID и метаданные, проверить связь с БД, не менять активные файлы. Сиротские и незавершённые записи показывать отдельно; импорт не должен создавать фиктивно завершённое интервью.
6. Не отправлять старые записи провайдеру автоматически при запуске. Восстановление существующих сессий должно быть явным действием пользователя с сохранённым согласием.

Приёмка: запуск из другого cwd не меняет расположение данных; оба процесса сообщают согласованный корень; файлы не перезаписываются конкурентно; существующие записи остаются доступны.

### B. Durable доставка чанков из desktop в backend

Статус: не начат. Зависит от A.

Файлы: Tauri native commands/session lifecycle, audio-capture spool interface, backend audio/chunks, Repository ingestion, worker STT.

1. Подключить отправитель к событиям завершения записи чанка. При запуске/восстановлении сканировать только завершённые файлы; временные файлы не отправлять.
2. Передавать существующий контракт: interview_id, track_id, capture_epoch, sequence, timestamps, format, sample_rate, channels, sample_count, checksum и bytes. Метаданные брать из spool, а не реконструировать по имени файла.
3. Сохранять подтверждение приёма локально. Удаление/перезапуск процесса после ответа сервера, но до записи ACK, приводит к безопасной повторной отправке.
4. Использовать ограниченное число одновременных запросов, timeout и backoff. Постоянный 4xx/конфликт содержимого показывать как ошибку, а не повторять бесконечно. Повтор того же чанка — идемпотентный успех.
5. ACK означает, что backend надёжно сохранил bytes, metadata и идемпотентное STT-задание. Проверить crash между записью файла и транзакцией БД; повтор должен завершать приём без дубля/потери.
6. Проверить путь raw PCM → корректный WAV → STT adapter, реальные timestamps и дорожку итогового сегмента. Не подменять формат расширением файла.
7. Прогресс показывать раздельно: записано, принято backend, ожидает STT, распознано, ошибка. Не удалять аудио сразу после ACK — применять существующую политику хранения.
8. Удаление интервью останавливает его отправитель; ответ 404/DELETED не вызывает бесконечный retry и восстановление удалённых данных.

Приёмка: реальная короткая запись создаёт audio_chunks и TRANSCRIBE_AUDIO jobs, после обработки — сегменты; потеря сети не останавливает локальную запись; повторная доставка и рестарт не дублируют результат. Проверки доставки с локальным stub STT отделены от проверки реального провайдера.

### C. Закрытие manifest и серверная готовность к ревью

Статус: не начат. Зависит от B.

Файлы: stop_capture, stopInterview, LiveSessionScreen, backend stop/status/jobs API, manifest storage.

1. Stop прекращает вход samples, дочитывает буферы, закрывает обе дорожки и возвращает реальные manifests/ссылки на них. Если остановка одной дорожки ошиблась, всё равно корректно остановить вторую и вернуть совокупный результат.
2. Сохранить manifests и состояние завершения так, чтобы после сбоя запрос можно было повторить. Не доверять произвольным track/path из payload; валидировать принадлежность, допустимые значения и полноту метаданных.
3. Backend проверяет приём ожидаемых чанков по дорожкам и epoch, sequence, checksum и sample count. Нулевое количество jobs не заменяет эту проверку.
4. Разделить processing-состояния: ожидаются чанки, STT выполняется, STT failed, запись имеет пробелы, готово. На ошибке дать retry либо явное решение о неполных данных с отражением в отчёте.
5. Удалить безусловный переход через 15 секунд. UI показывает длительную обработку и позволяет безопасно вернуться позже. Таймаут ожидания интерфейса не меняет статус интервью на REVIEW.
6. Сервер разрешает переход REVIEW только по проверенному состоянию. Общий `/status` не должен обходить readiness gate. Повтор stop/readiness безопасен.
7. Finalize также проверяет завершённость обязательной обработки и зафиксированные ограничения записи.

Приёмка: пропущенный чанк, failed STT и незакрытая дорожка блокируют обычный переход; после поступления последнего чанка и завершения STT появляется готовность; обработка дольше 15 секунд не выглядит завершённой; повтор stop не создаёт вторую сессию/manifest.

### D. Реальные аудиоисточники, телеметрия и ошибки старта

Статус: не начат. Зависит от A–C.

Файлы: commands.rs, CaptureHandle/telemetry, SetupScreen, AudioMeters, pause/resume handlers.

1. Убрать молчаливый fallback на default input. Недоступный выбранный источник — ошибка с предложением повторно выбрать устройство.
2. Не выбирать один микрофон за оба канала автоматически. Для рабочего двухканального сценария требовать осознанно настроенный вход кандидата; отсутствие loopback явно показать. Не называть любой второй input системным звуком.
3. Проверить согласованность start: при отказе открытия второго потока первый закрывается, backend не остаётся в ложном RECORDING. Повторный старт при активной сессии отклоняется, а не заменяет handle.
4. Получать RMS/peak и dropout/overflow/error из реальных samples с безопасным обменом между callback и UI. При отсутствии данных показывать unknown, а не healthy или фиктивную активность.
5. Pause/resume должны согласованно менять обе дорожки и серверный статус; при частичном отказе не показывать успешную паузу. Отдельно проверить timestamps и epoch после resume.
6. Ошибки устройств, spool и отправителя показывать по их источнику. Индикатор «идёт запись» не означает «STT работает».

Приёмка: несуществующее устройство не запускает микрофон вместо loopback; сигнал только на одном входе отражается только на соответствующей дорожке; отключение источника даёт ошибку; пауза и продолжение сохраняют корректный timeline. Реальную проверку начать с текущей macOS; другие ОС не объявлять проверенными.

### E. Оценивание по конкретному вопросу и активной ревизии

Статус: не начат. Зависит от B–C.

Файлы: pipeline._handle_evaluate, enqueue API, matcher/associations, evidence_validator, Live/Review UI.

1. В job фиксировать ожидаемые rubric/transcript revisions на сервере; не использовать константы `trans-rev-1`/`rub-rev-1` как замену актуальным входам.
2. Получать сегменты только указанной ревизии и привязки соответствующего вопроса. Использовать canonical prompt вопроса, а не рассчитывать на устаревшее поле text.
3. Удалить fallback на все candidate segments и произвольный candidate_text из payload в рабочем пути. Импорт текста, если нужен, проходит отдельный явный endpoint с provenance.
4. При отсутствии привязки запустить существующий matcher или запросить ручную привязку; при отсутствии ответа не вызывать модель ради выдуманной оценки.
5. Evidence разрешать только в выбранном интервью, ревизии и наборе связанных сегментов. Невалидные предложения остаются rejected и не попадают в итог.
6. Перед сохранением результата проверить актуальность входов; смена ревизии во время LLM-запроса не делает старый ответ актуальным. Не затирать human assessment.
7. UI отслеживает конкретный job и показывает отсутствие ответа/привязки, failed/rejected/completed. Надпись «отправлено» не равна «оценено».

Приёмка: два вопроса с разными ответами не получают чужие цитаты; старые версии текста не входят в новый запрос; неизвестная привязка не расширяется до всей стенограммы; поздняя оценка после изменения ревизии не перезаписывает актуальное решение.

### F. Восстановление сессии и обработки после reload/restart

Статус: не начат. Зависит от A–E.

Файлы: App.tsx, API-клиент, session state в Tauri, список интервью, uploader recovery.

1. При старте UI запросить backend-сессии и состояние native capture. Дать открыть существующее интервью и продолжить processing/review; не хранить единственный путь к нему в React state.
2. Сохранённый ID может использоваться как подсказка, но статус и данные перечитываются с backend. Удалённая сессия не восстанавливается по локальному ID.
3. Различать reload WebView при живом capture и полный перезапуск процесса. Reload подключается к текущему capture, не открывая вторые потоки.
4. После аварийного завершения показать незавершённую запись и реальные границы сохранившегося аудио. Не имитировать непрерывную запись и не включать микрофон автоматически.
5. Восстановить отправку неподтверждённых чанков и ожидание STT для явно выбранной сессии. Старые finished/finalized сессии открывать в соответствующем режиме.
6. Сохранить минимальный UI: список/выбор сессии и экран состояния. Полный редизайн навигации не нужен.

Приёмка: reload не теряет доступ к текущей сессии и не дублирует запись; restart позволяет открыть processing/review и завершить доставку; finalize/export прежней сессии доступны; удалённая сессия не воскресает.

### G. Настоящая сквозная проверка и исправление отчёта готовности

Статус: не начат. Зависит от A–F.

1. Сохранить существующие backend-тесты как проверки backend. Переименовать/уточнить описания, которые называют прямую вставку стенограммы проверкой desktop capture.
2. Добавить интеграционную проверку настоящего пути spool → native sender → HTTP ingestion → durable job → STT adapter → segment. Stub-провайдер допустим для повторяемой проверки, но не как доказательство внешней совместимости.
3. Провести реальный пользовательский сценарий в Tauri: выбор двух источников → согласие → запись → pause/resume → stop → ожидание доставки/STT → стенограмма → привязки → AI → ручное подтверждение → summary → finalize → export.
4. Для реального провайдера использовать специально созданную короткую тестовую запись, а не автоматически отправлять накопленные пользовательские записи. Зафиксировать успешные STT/LLM-вызовы и результат без секретов.
5. Повторить сценарий вторым интервью с теми же question IDs. Проверить независимость записей, транскриптов и итогов.
6. Проверить сеть offline/online, retry после потерянного ACK, закрытие приложения до доставки, failed STT, отсутствие loopback, stop на хвосте, обработку дольше 15 секунд и удаление во время retry. Для файловых аварий использовать временные каталоги.
7. Запустить необходимые Python/Rust tests и desktop typecheck/build. Сборка не заменяет запуск Tauri.
8. Обновить docs/stage9-verification-and-audit.md и README: отдельно реализовано, проверено автоматически, проверено реальной записью, не проверено. SHA-256 называть checksum, а не цифровой подписью.
9. Для каждого результата сохранить команды/сценарий, commit, ОС/источники, модель и наблюдаемые счётчики. Не ставить PASSED при пропуске реального шага.

Приёмка: из UI создана реальная запись, получены durable чанки, STT и отчёт; повтор и восстановление работают; ограничения подтверждены фактически. Сводка показывает не только число тестов, но и доказательство прохождения desktop-пути.

## 4. Регрессионная матрица

| Проверка | Ожидаемый результат |
| --- | --- |
| Запуск из другого cwd | Те же абсолютные пути данных |
| Законченный чанк в capture spool | Durable ACK и одно STT-задание |
| Повтор после потерянного ACK | Нет дубля чанка/сегмента |
| Другие bytes под тем же ключом | Конфликт, видимая ошибка |
| Сеть недоступна | Локальная запись продолжается, backlog виден |
| Stop при недоставленном чанке | Processing, не REVIEW |
| Пустая очередь и недостающий manifest | Не считается готовностью |
| STT failed или выполняется более 15 секунд | Видимое состояние, без ложного завершения |
| Отсутствующий loopback | Ошибка выбора, без fallback на микрофон |
| Сигнал только на одном входе | Реальный уровень только этой дорожки |
| Два вопроса/две ревизии | Оценка использует только свои актуальные сегменты |
| Reload WebView | Подключение к активной сессии без второго capture |
| Полный restart | Доступ к существующей записи и явное восстановление |
| Удаление во время доставки | Нет воскрешения данных и бесконечного retry |
| Два полных интервью | Раздельные записи, оценки и экспорты |

## 5. Контрольные точки завершения

- **Первая рабочая вертикаль (A–C):** реальный чанк из Tauri доходит до STT и виден текст; stop ждёт все обязательные данные.
- **Корректный сценарий (D–F):** достоверные источники/уровни, оценки по нужным ответам, восстановление состояния.
- **Подтверждённая готовность (G):** пользовательский путь пройден в приложении, а отчёт соответствует свидетельствам.

Если не прошла первая точка, дальнейшее увеличение количества тестов/документации не считается завершением интеграции. Этот план не включает новые модели, редизайн, облачную архитектуру и несвязанный рефакторинг.
