## Подтверждённые проблемы

### R1 — P1: `/stop` записывает манифест вне доверенного spool

Источник: `backend/api/app.py:1064–1070`. `manifests` принимается как список произвольных
словарей; `track_id` участвует в построении пути без enum/проверки корня. Абсолютный путь
сбрасывает предшествующие компоненты `Path`, а `..` позволяет выйти из каталога интервью.

Воспроизведение: TestClient с подменёнными repository/spool; `track_id` указывает на соседний
временный каталог. Получено HTTP 200; `outside/manifest.json` создан вне trusted spool.
Имя файла фиксировано, но каталог и JSON-содержимое контролирует вызывающий API.

Исправить:

- Типизировать stop payload существующим контрактом манифеста; принимать только ожидаемые
  для интервью дорожки, проверить interview ID, формат и согласованность счётчиков.
- Строить путь из серверных значений; проверять разрешённый корень, включая symlink.
- Валидировать все манифесты до изменения статуса, писать атомарно; повтор после сбоя
  должен безопасно доводить фиксацию до конца.

Приёмка: absolute path, traversal, чужой interview ID, unexpected track и symlink отвергаются;
файл вне spool не меняется; валидный повтор stop идемпотентен; ошибка записи не скрывается.

### R2 — P1: ручные изменения стенограммы не инвалидируют оценки

Источники: `backend/db/repository.py:410–546`, API `speaker-role` и `split`.
Смена роли и split изменяют сегменты на месте, не создают ревизию и не помечают зависимые
оценки stale. Есть fallback на сегмент из произвольной старой ревизии.

Воспроизведение: после сохранения human assessment и AI proposal сменить роль сегмента
`candidate → interviewer`. Результат: revision остаётся `trans-rev-1`, оба `is_stale = 0`.
Старая оценка продолжает учитываться, хотя её доказательство больше не является речью кандидата.
Split также может изменить текст/границы цитаты без изменения revision ID.

Исправить:

- Провести role/split через существующий механизм ревизий: expected revision в API/TS,
  транзакционная проверка актуальности, новая ревизия, сохранение исходных сегментов.
- Перенести/перепроверить associations и пометить зависимые proposals, human decisions и
  summary устаревшими. Ручное решение сохранить до явного повторного подтверждения.
- Убрать поиск в произвольной ревизии; поздний AI-ответ не должен сохраняться актуальным
  после такой правки. Финализация должна проверять фактические input revisions.
- При retranscription shared track не назначать всему смешанному сегменту роль по одному
  максимальному overlap (`pipeline.py:624–643`): конфликт ролей требует unknown/разделения
  и подтверждения человеком.

Приёмка: role change и split после review, конкурентный AI-ответ, запрос из старой вкладки,
старые/новые сегменты с одинаковым ID, смешанный shared segment. Старый снимок сохранён,
неактуальные решения не попадают в score/finalize.

### R3 — P1: обход происхождения evidence и привязки к вопросу

Источники: `backend/workers/pipeline.py:282–329,495–517`,
`backend/api/app.py:1171–1193`, `backend/db/repository.py:1732–1772`.

Подтверждено двумя stub-воспроизведениями:

- Пустая стенограмма + job payload `candidate_text='invented speech'`, `segment_id='fabricated'`:
  сохранено предложение `is_rejected=false`, `validation_errors=[]`, в БД ноль сегментов.
  Fallback для mock-тестов доступен через обычный enqueue endpoint.
- Для вопроса q1 stub вернул цитату из сегмента, связанного с q2. Предложение принято:
  валидатор получает все сегменты интервью, а не только допустимые для q1.

Дополнительно запрос отсутствующей ревизии расширяется на все сегменты;
associations читаются без revision filter, ручная перепривязка также не ограничена ревизией.

Исправить:

- Удалить production fallback `candidate_text`; тесты должны создавать настоящие временные
  сегменты/associations. Явный ручной импорт должен сохранять текст и provenance до оценки.
- Проверять question ID и фиксировать активные rubric/transcript revisions на сервере
  при enqueue; не расширять отсутствующий набор данных на другие ревизии.
- Ограничить evidence текущим вопросом и ревизией. Использовать один и тот же допустимый
  набор сегментов для запроса модели и программной валидации.
- Добавить revision scope и OCC к чтению/ручной смене associations; сохранить ручные связи.

Приёмка: оба воспроизведения отклоняются; q1/q2, две ревизии с одинаковыми segment IDs,
неизвестный вопрос, пустой ответ и запоздалый результат не смешивают evidence.

### R4 — P1: итоговое AI-резюме получает rejected/stale данные

Источники: `backend/workers/pipeline.py:746–782`,
`backend/db/repository.py:900–966`, `backend/db/schema.sql:107–118`.
Worker складывает все proposals, затем human assessments, не фильтруя rejected, stale,
ревизии и исключения. В summary storage нет привязки к ревизии входных решений;
`confirm_summary` обновляет все summary данного интервью.

Воспроизведение: генератор заменён stub; сохранён единственный rejected+stale proposal.
Он передан генератору как решение по вопросу. Это загрязняет текст резюме, даже если
детерминированный score правильно использует human assessments.

Исправить:

- Формировать summary из актуальных подтверждённых human decisions; исключённые/неполные
  вопросы передавать как ограничения, не как положительные или отрицательные оценки.
- Привязать summary к конкретным input revisions и версии/снимку human decisions;
  повторно проверить входы при сохранении и подтверждении. Правки review инвалидируют summary.
- Подтверждать конкретный summary ID, сохранять ручной текст отдельно от новых AI proposals.
- Проверять ссылки/цитаты результата программно по допустимым evidence.
- Если расширяется схема: bootstrap + последовательная миграция с сохранением данных.

Приёмка: rejected/stale/чужая ревизия не входят в prompt; исключение видно как ограничение;
правка оценки во время генерации даёт stale; старое подтверждение возвращает 409;
новая генерация не затирает ручное резюме.

### R5 — P1: lease не защищает сохранение результата, лимит попыток обходится

Источники: `backend/workers/pipeline.py:77–134`,
`backend/db/repository.py:1447–1615`. Lease берётся на 60 секунд; worker не вызывает
`renew_job_lease`. Результаты сохраняются до `complete_job`, и запись результата не проверяет
owner token. Просроченные PROCESSING выбираются без ограничения `attempts < max_attempts`.

Воспроизведение: job с `max_attempts=1`, первый claim с уже истёкшим lease, второй claim:
получено `attempts=2`. Статический путь также допускает запись результата прежним worker
после передачи lease другому; проверка owner при complete происходит слишком поздно.

Исправить:

- Продлевать lease во время долгих STT/LLM/batch операций, включая все сгруппированные jobs.
- Проверять owner и актуальность input revisions в транзакции записи результата;
  обеспечить идемпотентность результата по job, а не случайному proposal ID.
- При исчерпании попыток переводить expired job в terminal FAILED. Задать durable retry
  delay вместо немедленной повторной выдачи.
- Группировать только последовательные совместимые чанки одной дорожки/epoch; сейчас
  `claim_adjacent_transcribe_jobs` проверяет track после LIMIT и не проверяет последовательность.
  Освобождать/завершать все взятые jobs при silence break и ошибке STT.

Приёмка: два workers и управляемое истечение lease; первый не сохраняет поздний результат;
max attempts соблюдается после рестарта; группа с silence/error не оставляет лишние leases;
непоследовательные chunks не склеиваются как непрерывная речь.

### R6 — P1: сохранённый режим захвата не восстанавливается в Setup

Источники: `apps/desktop/src/screens/SetupScreen.tsx:52,105–117,279–312`,
`apps/desktop/src/services/api.ts:930–939`, `backend/api/app.py:467–499,698–707`.
Existing draft загружает имя/роль/план, но не capture mode. Локальный default — dual_source;
draft update также не сохраняет mode. Backend остаётся single_source и ждёт shared,
в то время как Tauri получает dual_source и пишет interviewer/candidate.

Исправить: восстанавливать mode из интервью; поддержать его изменение для draft/ready
сквозь DTO → repository → TS и атомарно обновлять expected_tracks. Перед start использовать
сохранённое серверное значение. После начала записи менять режим нельзя.

Приёмка: single draft → закрыть → открыть → start остаётся single; dual → single до start
обновляет expected_tracks; обе дорожечные конфигурации доходят до readiness.

### R7 — P2: reload теряет паузу, таймер и достоверный режим индикаторов

Источники: `apps/desktop/src/App.tsx:34–61,73–85`,
`apps/desktop/src/screens/LiveSessionScreen.tsx:30–31`,
`apps/desktop/src/components/AudioMeters.tsx:47–54`.
App игнорирует native `is_paused`/`elapsed_ms`; Live всегда начинает с false/0.
AudioMeters без явного mode определяет single_source по ненулевому shared RMS.

Исправить: гидратировать live state из native session и backend; передавать capture mode
явно через Header к meters. Тишина должна отличаться от отсутствующей telemetry.

Приёмка: reload paused session с ненулевой длительностью сохраняет кнопку, статус и время;
нулевой RMS в single_source не превращает интерфейс в dual_source.

### R8 — P1: доставка аудио и манифестов не переживает offline stop/restart

Источники: `apps/desktop/src/screens/LiveSessionScreen.tsx:150–166`,
`apps/desktop/src-tauri/src/commands.rs:330–351`, `backend/api/app.py:1045–1071`.
Native stop потребляет active session. Манифесты остаются только в локальной переменной
обработчика. Если HTTP stop не дошёл, повторный native stop возвращает пустые manifests.
Backend stop уже допускает повтор PROCESSING → PROCESSING; проблема не в state machine,
а в утрате результата и недоставленных манифестах.

Кроме того, uploader прекращает основной retry loop при stop, делает только один final
drain (`uploader.rs:121–132`) и завершает его на первой сетевой/HTTP-ошибке (`287–296`).
Непереданные чанки остаются локально без работающего отправителя. Единственное место
создания uploader — новый `start_capture` (`commands.rs:299–301`); открыть старое интервью
после restart недостаточно для возобновления доставки. Это статически прослеженный путь,
не результат сетевого теста в Tauri.

`SessionUploader::stop` (`uploader.rs:317–321`) ждёт handle не более 3 секунд и игнорирует
результат timeout. Это предел ожидания вызывающего кода, а не доказательство доставки
или явной отмены фоновой задачи. Сетевой timeout клиента — 10 секунд; stop может вернуть
управление до завершения текущего запроса. Просто увеличить final drain недостаточно:
нужно сохранить управляемое состояние доставки и возможность продолжения после deadline.

Исправить: сохранять результат native stop/манифесты до подтверждения backend; обеспечивать
восстановление из sealed spool после reload/restart. Разделить capture stopped, pending stop
delivery и ожидание readiness. Повторять нужный этап, не выполнять native stop заново.
Срок жизни uploader отделить от захвата; дать возобновить доставку существующего spool
без включения микрофона. Подтверждённые ошибки payload 400/422 переводить в атомарный `.err`
и учитывать в failed без бесконечных retries. 401/403 останавливают доставку с явной
ошибкой доступа и возможностью возобновления после исправления конфигурации; они не
доказывают повреждение аудиочанка. Network/408/429/временные 5xx обрабатывать повтором
с backoff и Retry-After, где он применим. Не классифицировать все 4xx одинаково.

Приёмка: обрыв до HTTP stop, потерянный ACK, reload между native stop и HTTP; все манифесты
доходят повтором, пользователь видит stopped/processing, а не ложную активную запись.
Stop при offline → online и restart с backlog приводят к доставке всех chunks без
повторной записи; 422 виден как terminal failure, удалённая сессия не восстанавливается.
Mock HTTP-сценарии: network error/503 во время stop → восстановление → eventual ACK;
422 → один failed record без повторной отправки; 429 → отложенный повтор; 401/403 →
видимая блокировка доступа без порчи spool. Проверить запрос дольше 3 секунд и отсутствие
конкурирующих отправителей после возобновления.

Отдельный restart-тест: заранее создать валидные `.chunk/.meta.json` без `.ack` во временном
spool существующего интервью; создать новое состояние приложения без active capture.
После startup recovery либо явной команды retry mock HTTP должен получить chunk POST,
а durable ACK — появиться на диске. Простого вызова `get_upload_progress` недостаточно:
подсчёт файлов не запускает отправителя. Проверить sealed и unsealed pending sessions;
для unsealed не выдумывать финальный manifest, а явно показать незавершённую запись.
Повторный recovery не создаёт второй uploader для того же интервью, микрофон не включается,
удалённые/финализированные интервью не возобновляются как активные записи.

### R10 — P2: spool не обеспечивает согласованную публикацию payload/metadata

Источники: `crates/audio-capture/src/spool.rs:81–97,135–150`,
`apps/desktop/src-tauri/src/uploader.rs:178`. Payload публикуется rename до записи metadata,
а metadata пишется напрямую. Uploader обнаруживает только `.meta.json`. При падении между
операциями сохранённый `.chunk` остаётся необнаружимым; оборванный JSON также требует recovery.
Manifest пишется напрямую и не создаёт track directory: остановка до первых samples на
новой дорожке завершается ошибкой sealing. Вывод по коду, crash/hardware тест не выполнялся.

Исправить: сделать metadata атомарным маркером готовности, определить порядок durable
записи и recovery для orphan payload/незавершённой пары; повреждение не должно скрываться.
Создавать каталог и атомарно публиковать manifest даже при нуле chunks.

Приёмка: fault injection между каждой записью/rename, restart и повторный scan; сохранённые
данные либо восстанавливаются с корректной metadata, либо явно отмечены как incomplete.
Пустой track закрывается корректным нулевым manifest, а не выдуманной успешной записью речи.
Отдельный unit-сценарий: новый временный spool, пустой consumer, stop до первого callback;
worker успешно возвращает zero-sample stats, существует sealed manifest с нулевыми счётчиками.

### R11 — P2: native session и аудиочанки расходятся по capture epoch после resume

Источники: `apps/desktop/src-tauri/src/commands.rs:228,274,284,628,654`,
`crates/audio-capture/src/capture.rs:134–144,256–259`, `crates/audio-capture/src/clock.rs:4–11`.
Worker получает обычный clone clock; pause/resume изменяет только session clock.
После resume IPC показывает следующий epoch, а chunks и manifest продолжают использовать
epoch копии, созданной при start. Статически подтверждено; реальные паузы устройства не проверены.

Исправить: согласовать контракт epoch и активного timeline между session и capture workers;
передавать смену epoch на границе обработки аудио, согласовать sequence/manifest/readiness
и правило обработки неполного чанка на паузе. Не менять только возвращаемое IPC-число.

Приёмка: pause/resume и несколько пауз на хвосте чанка; epoch в native state, metadata,
DB и manifest согласован, интервалы не перекрываются, samples не теряются и не дублируются.

### R12 — P2: начальный offset фиксируется до открытия аудиопотока

Источники: `apps/desktop/src-tauri/src/commands.rs:222–230,268–285`,
`crates/audio-capture/src/capture.rs:361–450`. `mark_track_start` вызывается перед
`start_device_capture`, который ещё получает конфигурацию, создаёт поток и вызывает play.
Поэтому timestamp отражает начало процедуры открытия, а не начало захваченных samples.
При разной startup latency устройств межтрековый offset расходится с фактическим;
это отдельная проблема от несогласованного epoch после resume. Вывод по коду,
величина ошибки на физических устройствах не измерена.

Исправить: привязать начало timeline к первому захваченному sample через доступный
timestamp аудиобэкенда и согласовать его с монотонным временем интервью. Метка после
успешного `stream.play()` — лишь приближение: она не доказывает время первого sample.
Явно определить точность и поведение при отсутствии callbacks; не заменять такую запись
фиктивным подтверждённым start offset. Передавать установленную метку в capture worker
и session state до публикации соответствующей metadata.

Приёмка: управляемая задержка открытия второго устройства и отдельно задержка первого
callback; metadata соответствует моделируемому времени samples, а не началу open/play.
Проверить shared и dual tracks, отсутствие callbacks и согласованность вычисленного skew.
Hardware-проверкой отдельно измерить фактическую точность синхронизации дорожек.

## Порядок реализации и контрольные точки

Все этапы ниже — **не начаты**. На каждом этапе сначала воспроизводящий тест, затем
минимальная правка, проверка и обновление статуса. Не расширять задачу на UI-редизайн,
новых провайдеров или общий рефакторинг.

1. **R1:** закрыть запись за пределами spool и безопасно фиксировать stop-манифесты.
2. **R2–R3:** восстановить целостность ревизий, роль кандидата и область evidence.
3. **R5, R10–R12:** защитить результаты ownership/идемпотентностью, spool, epoch и start offsets.
4. **R4:** построить summary на проверенных актуальных решениях и добавить OCC.
5. **R6–R8:** согласовать mode, reload, stop/recovery через UI/API/Tauri.
6. **R9:** восстановить обязательные lint/format gates, запустить полную регрессию.
7. **Сквозная приёмка:** повторить два интервью, single/dual, role/split после review,
   долгий STT, offline stop, reload paused session, restart и finalize/export.

Для изменений API/repository/contracts/worker обязательны полный pytest и Ruff;
для Rust — cargo fmt/test; для desktop — build и соответствующие контрактные сценарии.
Последний этап отдельно требует ручного Tauri/hardware прогона. Provider probe проводить
только при необходимости на специальной синтетической записи, с фиксацией точной пары
provider/model. Автоматические тесты и build не заменяют эти доказательства.
