# План: уточняющие и наводящие вопросы по ответам кандидата

Дата: 2026-09-11. Основание: код на коммите `944b255`.
Статус: план для реализации другим агентом; функциональность ещё не реализована.

## 1. Цель и принятые продуктовые решения

Во время интервью AI предлагает интервьюеру, что спросить дальше по текущему
вопросу плана: уточнить неоднозначность, проверить глубину понимания или мягко
направить кандидата. Интервьюер сам выбирает формулировку и произносит вопрос.

Пользователь подтвердил два способа запуска: **автоматически после ответа
кандидата и по кнопке**. Остальные решения ниже — предлагаемые границы первой
версии, а не уже существующее поведение продукта.

- Автоматически предлагать до двух вопросов типов `clarify` и `deepen`.
- Кнопка «Предложить вопросы» запускает тот же механизм вручную.
- Отдельная кнопка «Мягко направить» запрашивает один вопрос типа `guide`.
  Не включать наводящие вопросы в автоматический режим: они могут раскрывать
  часть решения и менять условия оценки.
- Подсказки относятся к выбранному вопросу утверждённого плана. Они не становятся
  новыми `PlannedQuestion`, не добавляют критерии и не меняют веса или coverage.
- Автоматический запуск работает, пока открыт экран живого интервью и включён
  переключатель «Автоподсказки»; по умолчанию он включён. При закрытии экрана новые
  автоматические запросы не создаются, уже принятые задания остаются в durable queue.
- Генерация разрешена в `RECORDING`; ручной запрос также разрешён в `PAUSED`.
  В `PROCESSING` и `REVIEW` доступна история, без новой генерации.
  Отметки карточек изменяются в `RECORDING`/`PAUSED`; в `REVIEW` допустима правка
  уже записанной истории, но не новое действие «Задан» для неиспользованной карточки.
- Не требовать предварительной AI-оценки ответа: её задержка или ошибка не должна
  блокировать уточняющие вопросы.

Пример, иллюстрирующий поведение, а не фиксированный набор шаблонов:

| Ответ кандидата | Тип | Предложение интервьюеру |
| --- | --- | --- |
| «Индекс ускоряет поиск» | `deepen` | «В каких случаях индекс может замедлить работу базы и почему?» |
| «Кэш решает проблему нагрузки» | `clarify` | «Что именно вы будете кэшировать и как определите срок актуальности?» |
| «Не знаю, как избежать повторной обработки сообщения» | `guide`, только по кнопке | «Как можно понять, что это сообщение уже обрабатывалось раньше?» |

Карточка содержит вопрос, короткое «Что проверяем», тип и ссылку на фрагмент
ответа, который послужил основанием. В ней нет готового эталонного ответа,
внутренних reasoning traces или вердикта о кандидате.

Не использовать общий `/jobs/enqueue` как публичный контракт подсказок:
свободный payload не должен позволять подставлять текст кандидата, чужую ревизию
или обходить ограничения новой операции.

## 3. Архитектура первой версии

```mermaid
flowchart LR
    T[Подтверждённые реплики и связи] --> C[Контекст выбранного вопроса на backend]
    U[Live UI: автоматический триггер или кнопка] --> P[Типизированный POST]
    C --> P
    P --> Q[Существующая jobs: GENERATE_FOLLOWUPS]
    Q --> W[Отдельный consumer для подсказок]
    W --> L[Существующий LLM adapter]
    L --> V[Проверка структуры, цитат и актуальности]
    V --> D[SQLite: запрос и предложения]
    D --> U
    U --> H[Интервьюер отмечает заданный вопрос]
    H --> R[История в Review и снимке отчёта]
```

Не вводить агентный framework, tools loop, vector DB, отдельный сервис,
WebSocket/SSE, новые модели или изменения захвата аудио. Это одна ограниченная
LLM-операция с программной проверкой результата.

Основную предметную логику разместить в `backend/core/followup_generator.py`:
сбор контекста из переданных данных, fingerprints, prompt и проверку предложений.
I/O и транзакции остаются в repository, работа с провайдером — в worker/adapter.
Не превращать модуль в универсальный слой оркестрации AI.

### 3.1. Контекст вопроса и роли

Backend самостоятельно читает активные rubric/transcript revisions, план,
финальные сегменты и связи текущего интервью. Клиент передаёт только идентификаторы
и выбранный режим; произвольный `candidate_text` не принимается.

Правила отбора:

1. `question_id` существует в активном плане именно этого интервью.
2. Учитываются только `is_final=true` сегменты текущей transcript revision.
3. Явная роль `candidate` разрешает использовать реплику как ответ; явная роль
   `interviewer` исключает её даже на дорожке `candidate`. При роли `unknown`
   дорожка `candidate` может использоваться по существующему правилу dual source,
   но `shared/unknown` никогда не становится кандидатом автоматически.
4. Ручная связь сегмента с вопросом имеет приоритет. Для остальных сегментов
   можно вычислить связи существующим matcher-ом в памяти, с текущими ролями.
   Не перезаписывать ручные связи и не вызывать мутирующий GET `/associations`
   из нового пути чтения.
5. Неоднозначные автоматические связи не использовать как достоверный ответ.
   Если пригодных реплик нет, вернуть понятную причину и не вызывать LLM.
6. Реплики интервьюера передавать отдельно как контекст вопроса, а не evidence.
   Ограничить их тем же вопросом и временным диапазоном выбранного ответа.
7. В контекст включить основной вопрос, критерии, роль позиции и недавние
   заданные/отклонённые уточнения по нему. Имя кандидата и всё интервью не нужны.

В UI дать действие «Отнести к текущему вопросу» для выбранной финальной реплики,
используя существующий `reassociateSegment` и OCC по transcript revision.
В этом пути проверять принадлежность целевого вопроса плану на сервере.
Назначение роли остаётся отдельным явным действием человека. Для `shared/unknown`
показать «Назначьте реплики кандидата»; при неоднозначной связи — «Укажите, к какому
вопросу относится ответ».

Ограничить вход детерминированно: брать самые свежие целые реплики текущего вопроса
в хронологическом порядке, сохранять их IDs и отметку усечения контекста.
Начальный предел — 12 000 символов текста ответа, 2 000 символов реплик интервьюера
и 20 последних решений по подсказкам. Дополнительно учитывать бюджет профиля
с резервом для prompt, rubric и output. Если даже один необходимый сегмент/план
не помещается, возвращать `context_too_large`, без молчаливой обрезки цитат.
Это границы MVP; полноту очень длинного ответа без отдельной суммаризации не обещать.

### 3.2. Автоматический запуск и частота

Надёжного события «кандидат закончил полный ответ» сейчас нет. Финальный STT-segment
означает завершённый блок распознавания, а не завершение мысли; assembler также
может разрезать длинную речь. Для MVP использовать явно описанную эвристику:

- Live UI получает серверный `candidate_fingerprint` для выбранного вопроса.
- При изменении пригодного ответа ждёт 3 секунды без новых изменений этого
  fingerprint и отправляет автоматический запрос режима `probe`.
- По умолчанию между автоматическими генерациями одного интервью не менее
  30 секунд. Числа — начальные настройки, а не измеренная гарантия качества.
- Одновременно допускается одно незавершённое follow-up задание на интервью.
  Изменившийся контекст не создаёт цепочку задач: после завершения текущей UI
  проверяет последний ответ и при необходимости запрашивает его.
- И debounce на клиенте, и серверные дедупликация/cooldown обязательны: remount,
  reconnect, две вкладки и повторный POST не должны умножать LLM-вызовы.
- Ручной запрос обходит автоматическую задержку, но не ограничение concurrency
  и не дедупликацию идентичного запроса. Повтор по тем же входным данным возвращает
  существующий результат. Бесконечные «другие варианты» в MVP не нужны.
- Смена выбранного вопроса сама по себе не считается новым ответом. Можно показать
  сохранённые предложения по нему и запустить генерацию по ещё не обработанному
  пригодному ответу после debounce.
- На паузе нет новых автоматических запросов. На stop/unmount отменяются клиентские
  таймеры. Поздний ответ для вопроса A не показывается в панели вопроса B.

Не сохранять выбранный UI-вопрос в `interviews`: backend проверяет явно переданный
`question_id`, а автоматическая генерация без открытого Live UI не входит в MVP.

### 3.3. Fingerprints и устаревание

Нужно различать входные данные, их дополнение и исправление:

- `candidate_fingerprint`: стабильный hash пригодного ответа выбранного вопроса;
  используется для автоматического триггера, не меняется от polling или создания
  самой подсказки. Учитывает IDs, текст, роли, принадлежность вопросу и revisions.
- `context_hash`: hash канонического снимка фактического входа LLM, включая вопрос,
  критерии, режим, отобранные реплики, историю решений и версии prompt/schema.
  Используется для идемпотентности. Генерировать hash на backend, без случайного
  UUID как единственной защиты от повторов.
- Запрос сохраняет собственный ограниченный снимок контекста. При исполнении
  и перед commit проверяются существование интервью, статус, обе revisions,
  содержимое/роли/связи всех исходных сегментов и актуальность истории решений.
  Не держать DB-транзакцию во время сетевого запроса.
- Новые реплики после границы снимка не делают старые цитаты недействительными:
  результат можно сохранить с признаком `has_new_answer=true` и временем
  последнего учтённого фрагмента. Затем обновить по cooldown. Иначе непрерывная
  речь будет постоянно обесценивать все незавершённые генерации.
- Изменение текста исходного сегмента, роли, связи, rubric или transcript revision
  делает предложение `stale`. Устаревший результат не показывается как актуальный
  и не допускает нового действия «Задан». Ответ старого worker-а не заменяет новый.
- Факт ранее заданного вопроса сохраняется и при stale: это история действий,
  а не заново вычисляемая оценка.

Историю решений проверять как часть входа незавершённой генерации. После её
успешного сохранения отметка «Задан» у самой карточки или её соседей не должна
делать весь набор stale: актуальность готового набора определяется источниками,
а решения управляют видимостью и дедупликацией следующих запросов. Не сравнивать
готовый результат с полным новым `context_hash` как единственный критерий stale.

Для MVP актуальность можно вычислять общей проверкой при чтении, исполнении
и действии пользователя. Это позволяет не добавлять новую ветку invalidation
в каждую существующую операцию редактирования транскрипта. Проверка при записи
выполняется атомарно на текущих данных; одного клиентского stale-флага недостаточно.

## 4. Контракты, хранение и API

### 4.1. Типы

Добавить отдельные Pydantic-модели в `contracts/domain.py` либо небольшой
`contracts/followups.py`, а соответствующие TypeScript-типы — в `src/types/index.ts`.
Не расширять `AssessmentProposal` полями нового независимого результата.

Минимальная модель предложения:

```text
FollowUpSuggestion
  id, request_id, interview_id, question_id
  rubric_revision_id, transcript_revision_id
  kind: clarify | deepen | guide
  question_text: 1..400 символов после strip
  purpose: 1..240 символов, короткое объяснение для интервьюера
  criterion_ids: непустой список IDs критериев текущего вопроса
  source_refs: 1..3 EvidenceRef из переданного ответа кандидата
  status: suggested | asked | dismissed
  asked_text: фактическая формулировка, если интервьюер её изменил
  decided_at, decision_version
  created_at
```

`is_stale`, `stale_reason`, `has_new_answer` — серверные поля представления.
IDs, версии, kind разрешённого режима, provider/model metadata и статусы задаёт
или проверяет backend; LLM не назначает идентичность и человеческие решения.

Выход LLM: `suggestions` от 0 до 2 для `probe`, от 0 до 1 для `guide`.
Пустой список — корректный результат «Полезных уточнений пока нет», а не ошибка
и не требование выдумать вопрос. Ошибку схемы/провайдера нельзя выдавать за пустой
успешный результат. Не принимать дополнительные поля (`extra="forbid"`).

### 4.2. Данные и миграция

Добавить две таблицы в bootstrap schema и следующую миграцию:

- `followup_requests`: ID, `interview_id`, `question_id`, обе revisions, `mode`,
  `trigger` (`auto|manual`), `candidate_fingerprint`, `context_hash`,
  ограниченный `context_json`, `job_id`, outcome (`ready|no_suggestions|superseded`
  или NULL до результата), фактические provider/model/profile IDs, версии
  prompt/schema, время создания/завершения, доступные usage/latency metadata.
- `followup_suggestions`: поля карточки и человеческого решения из контракта;
  `criterion_ids` и `source_refs` допустимо хранить как JSON по стилю проекта.

Статус исполнения и attempts брать из `jobs`, не дублировать вторую машину
состояний очереди в `followup_requests`. `failed` для клиента определяется по job;
`superseded` означает корректно прекращённую обработку изменившегося контекста.

Требования к repository:

- UNIQUE по `(interview_id, question_id, mode, context_hash)` и уникальная связь
  request → job. Стабильные IDs карточек по request + ordinal.
- Атомарно проверять существующий запрос, cooldown, незавершённые jobs и создавать
  request + job; использовать write transaction/`BEGIN IMMEDIATE` там, где это
  нужно для защиты check-then-insert при двух клиентах. Не вызывать вложенные
  repository-транзакции с отдельными соединениями из этой операции.
- Записывать полный проверенный набор карточек одной транзакцией, сверяя действующий
  lease/owner token и контекст. Retry после сбоя не создаёт дубликаты и не сбрасывает
  `asked`, `dismissed` или `asked_text`.
  Если результат уже сохранён, а job ещё не отмечена завершённой, повторный worker
  завершает job без нового LLM-вызова. После падения между ответом провайдера
  и commit повторный upstream-вызов возможен: exactly-once для сети не обещать.
- Человеческое решение — OCC по `decision_version`; повтор того же действия
  идемпотентен. Разрешить отмену ошибочной отметки с новой версией и audit event.
- Foreign keys/cascade на интервью и запрос; запросы, карточки и любые источники
  всегда выбирать с `interview_id`. Удалённое интервью не восстанавливается job-ой.
- Индексы для получения последнего запроса и истории по `(interview_id, question_id)`.
- Миграция повторно безопасна; проверить и `integrity_check`, и `foreign_key_check`.
  Существующие планы, оценки, jobs и запечатанные отчёты сохраняются.

### 4.3. HTTP API

Базовый путь: `/api/v1/interviews/{interview_id}`.

| Метод и путь | Контракт |
| --- | --- |
| `GET /followups?question_id=...&mode=probe` | Чистое чтение: доступность контекста/причина ожидания, revisions, `candidate_fingerprint`, `context_hash`, последний request и статус job, актуальные карточки, `has_new_answer`, история решений по вопросу независимо от режима. Не вызывает LLM и не создаёт связи. |
| `POST /followups/generate` | `question_id`, `mode=probe|guide`, `trigger=auto|manual`, ожидаемые revisions и `expected_context_hash`. Backend пересобирает контекст. Новый запрос — 202 с `request_id`/`job_id`; идентичный принятый запрос — тот же ID. |
| `PATCH /followups/{suggestion_id}` | `status`, при необходимости `asked_text`, `expected_decision_version`, ожидаемые revisions. Сохраняет решение и возвращает новую версию. |
| `POST /followups/requests/{request_id}/retry` | Только явный повтор terminal failure при всё ещё пригодном контексте; та же сущность/карточки, атомарный сброс retry budget. Не оживляет stale или completed запрос. |

Ошибки: 404 — чужая/отсутствующая сущность; 409 — OCC, изменившийся контекст или
запрещённый lifecycle; 422 — неверные поля. Cooldown/busy — структурированный
ответ с причиной, существующим request ID и временем следующей попытки, без
дополнительной job. Отсутствие пригодного ответа — штатное `waiting_for_candidate`
или `needs_association`, без обращения к провайдеру.

В общем `/jobs/enqueue` явно запретить `GENERATE_FOLLOWUPS` либо направлять его
через ту же проверенную repository-операцию. Не оставлять обход dedicated API.
Для live polling добавить чтение `/followups` в существующий цикл; не создавать
независимый бесконтрольный таймер. Защититься от перекрывающихся запросов и поздних
ответов после смены `interview_id`/`question_id`.

## 5. Worker, LLM и качество вопросов

### 5.1. Очередь и задержка STT

Добавить обработчик `GENERATE_FOLLOWUPS` в `PipelineWorker` и фильтр типов в
`Repository.claim_next_job`. В штатном worker-процессе запускать два ограниченных
consumer-а: существующий путь исключает новые follow-up jobs, второй берёт только
их и имеет concurrency 1. Существующие lease/heartbeat/reclaim использовать
для обоих путей. Это узкое расширение текущей очереди, без нового демона и брокера.

У consumer-а подсказок должен быть свой экземпляр LLM adapter: у resilient adapter
есть изменяемая `last_fallback_event`, которую нельзя смешивать между конкурентными
запросами. Не удерживать SQLite connection/transaction через `await` провайдера.
Фильтр claim должен одинаково работать для pending и expired jobs; условия SQL
с `OR` заключить в скобки до добавления фильтра типов.

Для MVP использовать существующий настроенный primary profile через
`OpenAICompatibleAdapter`, без каскада из трёх моделей на каждую live-подсказку.
Начальные ограничения: output до 1 024 токенов, общий deadline одной попытки
20 секунд, до двух durable job attempts. Не умножать этот бюджет внутренними
HTTP retries: текущий `execute_request(max_retries=1)` делает одну попытку;
transient retry выполняет очередь. Capability flags профиля
сохранить; не включать JSON Schema/reasoning/SSE по предположению.

Auth/config ошибки делать terminal без бессмысленных повторов; timeout/429/5xx
повторять в пределах бюджета с backoff через существующий `retry_delay_sec`
в `fail_job`, учитывая `Retry-After`. Сейчас worker этот параметр не передаёт,
поэтому одно лишь переиспользование его catch-блока durable backoff не обеспечит.
Добавлять только минимальный параметр
terminal failure в существующий `fail_job`, если текущий контракт не позволяет
выразить это. Сохранить поведение старых callers.

Перед вызовом и при commit проверять lifecycle. При переходе в `PROCESSING`,
`REVIEW`, `FINALIZED` или `DELETED` не публиковать новые предложения. Подсказки
не входят в STT readiness gate и не мешают остановке, review и финализации.
В памяти process cancellation должен корректно остановить новый consumer;
незавершённые задания восстанавливаются через lease после перезапуска.
При завершённом lifecycle можно убрать job из очереди по её существующему
служебному протоколу; не дописывать карточки/историю в финализированное интервью.

### 5.2. Prompt и проверка результата

Prompt задаёт профессиональную тему, текущий вопрос, критерии, режим и короткую
историю. Transcript оформляется как недоверенные данные: инструкции внутри речи
не выполняются. Реплики кандидата и интервьюера явно разделены.

Правила генерации:

- Один конкретный вопрос на карточку, в языке текущего интервью; для существующего
  русскоязычного workflow — по-русски. Сложность соответствует вопросу и rubric.
- `clarify`: прояснить значение сказанного, допущение, личный вклад или пример.
- `deepen`: проверить причинность, ограничения, компромиссы, альтернативу или
  применение знания в изменённых условиях.
- `guide`: предложить один небольшой шаг размышления, без полного решения и
  без утверждения, что кандидат сам его нашёл.
- Не повторять основной вопрос, уже заданное уточнение или фактически отвеченный
  аспект. Не делать вывод «не знает» только из отсутствия упоминания в коротком
  фрагменте; формулировать непроверенный аспект как цель уточнения.
- Только компетенции текущего вопроса, без персональных характеристик кандидата.
- `purpose` — короткое публичное объяснение пользы вопроса, не цепочка рассуждений.

После Pydantic-валидации проверить: разрешённый kind/количество, критерии текущего
вопроса, все source IDs внутри фактического снимка и candidate speech, наличие
цитаты в соответствующем тексте. Переиспользовать существующую проверку цитат,
учитывая, что она нормализует регистр/пробелы, а не проверяет byte-for-byte равенство.
Отсеивать точные нормализованные повторы основного/заданного/отклонённого вопроса
и повторы внутри набора. Если после удаления повторов ничего нет, допустим
`no_suggestions`; невалидные цитаты/структуру считать ошибкой валидации.

Не добавлять второй LLM-«судью». Семантическая полезность и отсутствие утечки
ответа не гарантируются одной schema или совпадением цитат: нужны сценарные
проверки, затем пилот и решение интервьюера.

В runtime logs/audit для новой операции писать IDs, исход, latency/usage и
безопасный код ошибки; не выводить полный prompt, ответ кандидата, upstream body
или секреты через необработанный `str(exc)`. Снимки контекста остаются в локальной
DB по правилам хранения интервью и не попадают в репозиторий.

## 6. Интерфейс, история и влияние на оценку

Добавить компактный блок «Что спросить дальше» в правую колонку LiveSessionScreen,
рядом с существующей оценкой. При необходимости выделить один компонент
`FollowUpSuggestions.tsx`, поскольку экран уже большой; редизайн остальных экранов
не входит в задачу.

Нужные состояния: ожидание ответа, необходимость назначить роль/связь, debounce,
в очереди, генерация, 0–2 предложения, обновившийся ответ, stale, ошибка и retry.
Не скрывать предыдущие пригодные предложения во время обновления; показывать
до какого момента ответа они построены. Метки времени брать из audio timeline,
а не из wall-clock времени прихода STT.

Действия карточки: «Задан», «Не подходит», переход к исходной цитате; при отметке
«Задан» можно отредактировать произнесённый текст. Клик не синтезирует реплику
в транскрипте и не доказывает, что вопрос реально прозвучал: это отметка человека.
Для `guide` показывать нейтральную метку «Наводящий вопрос».

Сохранить эту историю в ReviewScreen по основному вопросу. Если отмечен заданным
`guide`, показывать «Использован наводящий вопрос — учтите помощь при оценке».
Не утверждать, что любой последующий ответ получен благодаря подсказке: точной
привязки действия UI к произнесённому вопросу в MVP нет.

В первой версии scoring, веса, coverage и AI-оценку автоматически не менять.
Интервьюер видит помощь и использует существующие подтверждение/ручную правку
оценки. Метаданные подсказок никогда не становятся candidate evidence. Более
сложное автоматическое различение самостоятельного и подсказанного знания
потребует отдельного продуктового решения и не входит в этот план.

При финализации добавлять историю отмеченных заданными уточнений, включая
`kind`, `asked_text`, исходные revisions и время отметки, в canonical snapshot
до вычисления checksum. Для старых snapshots отсутствующее поле означает пустую
историю; не пересчитывать сохранённые checksum. Экспорт и просмотр исторического
отчёта читают эту историю из выбранного snapshot, а не из текущих живых таблиц.
Для финализированного интервью все изменения follow-up данных запрещены.

## 7. Порядок реализации

Исполнитель сначала перечитывает `AGENTS.md`, сверяет текущий код и `git status`.
Не использовать пользовательскую SQLite DB как тестовую. Шаги ниже — зависимости,
а не требование заводить отдельную абстракцию или большой PR на каждый шаг.

1. [ ] **Контракты и контекст.** Зафиксировать types, режимы, lifecycle, бюджеты;
   реализовать чистый сбор контекста, fingerprints, prompt и validator. Покрыть
   роли, ambiguous/manual associations, границы вопросов и формат результата.
2. [ ] **Хранение.** Schema + migration, атомарное request/job creation,
   дедупликация, чтение состояния, owner-guarded save и решения с OCC.
   Проверить новую и мигрированную временные DB, restart/retry и cascade delete.
3. [ ] **Worker.** Новый handler, отдельный ограниченный consumer, фильтр claim,
   deadline/retry budget и проверки актуальности до/после LLM. Заблокированный
   mock LLM не должен останавливать обработку нового STT-задания.
4. [ ] **API.** Dedicated endpoints, обработка ошибок и защита общего enqueue
   от обхода. Выполнить API → queue → worker → storage сценарий с mock provider.
5. [ ] **Desktop.** Типы/клиент, блок предложений, auto + manual, управление
   источниками, отмена таймеров, поздние ответы и отображение ошибок.
6. [ ] **Review и отчёт.** История заданных уточнений, явная метка помощи,
   snapshot/export без изменения формулы оценки и исторических отчётов.
7. [ ] **Регрессия и handoff.** Выполнить проверки ниже, обновить описание
   workflow/контрактов и отметить каждый завершённый шаг сразу после проверки.
   В отчёте перечислить реально выполненные и невыполненные виды верификации.

Наиболее затронутые существующие файлы: `contracts/domain.py`,
`backend/api/app.py`, `backend/db/{schema.sql,migrations.py,repository.py}`,
`backend/workers/pipeline.py`, `apps/desktop/src/{types/index.ts,services/api.ts}`,
`apps/desktop/src/screens/{LiveSessionScreen,ReviewScreen}.tsx`.
`contracts/provider.py` и `backend/core/profiles.py` расширять task type/route
только согласованно с реально используемым способом выбора профиля; наличие
`TaskRoute` само по себе не означает, что worker исполняет маршрутизацию из него.

## 8. Проверки и критерии приёмки

Добавить `tests/test_followup_questions.py`, `tests/test_followup_repository.py`
и `tests/test_followup_api.py` либо эквивалентные небольшие группы в принятых
проектом файлах. Все автоматические сценарии используют mock LLM и временную DB.

Обязательные проверки:

- Ответ по Q1 даёт предложения только по Q1 и его критериям; источник Q2 или
  другого интервью отклоняется даже при совпадении segment/revision IDs.
- `shared/unknown`, interviewer и partial не становятся основанием. Явное
  назначение роли и ручная привязка разрешают генерацию; ручные связи сохраняются.
- Фальшивая цитата, чужой criterion ID, лишние поля, неверный kind, переполнение
  лимитов и malformed JSON не публикуются. Корректный пустой ответ отличается
  от provider failure. Тест prompt injection проверяет разделение сообщений:
  речь не подставляется в system-инструкции; иммунитет самой модели это не доказывает.
- Одни и те же входные данные, два одновременных POST, reconnect/remount,
  повтор после сбоя commit не создают дубликаты requests/jobs или карточек.
- Дополнение live-транскрипта без новой revision меняет candidate fingerprint.
  Исправление текста/роли/связи без изменения ID выявляется проверкой snapshot.
- Новый фрагмент во время LLM допускает результат с `has_new_answer`; правка
  источника, role change, split, retranscription или новая rubric не допускает
  публикации старого результата как актуального.
- Потеря lease, reclaim, failure последней попытки, deadline и restart не теряют
  job молча. Старый owner не сохраняет результаты. Retry не стирает решения.
- Долгий follow-up LLM не блокирует STT; фильтр типов работает и для expired jobs.
  Pause/stop/review/finalization не ждут генерации подсказок.
- `asked`/`dismissed`, редактированный текст и отмена отметки сохраняются после
  перезагрузки и соблюдают OCC. Чужая карточка недоступна через вложенный URL.
- После `FINALIZED`/`DELETED` API и запоздалый worker не меняют данные. История
  snapshot и checksum прежнего отчёта неизменны после reopen и новых решений.
- При неизменных человеческих оценках `final_score` и coverage до/после использования
  уточняющих и наводящих вопросов полностью совпадают; речь AI не попадает в evidence.

Для содержательного качества завести небольшие синтетические fixtures: поверхностный
ответ, уверенный глубокий ответ, противоречие, «не знаю», уже заданный follow-up,
ответ на соседний вопрос, неоднозначная роль, слишком длинный ответ. Проверять
детерминированные ограничения тестами; полезность вопросов оценивать человеком.
Не писать тесты, утверждающие семантическое качество на основании одного mock JSON.

Команды после реализации затронутых backend/desktop слоёв:

```bash
uv run ruff check .
uv run pytest -q tests/test_followup_questions.py tests/test_followup_repository.py tests/test_followup_api.py
uv run pytest -q
npm --prefix apps/desktop run build
git diff --check
git status --short
```

Если зависимости ещё не установлены, выполнить стандартные `uv sync` и
`npm --prefix apps/desktop ci`. Rust не требуется менять по этому плану; если
исполнитель всё же затронет Rust/IPC, обязательны `cargo fmt --all -- --check`
и `cargo test --workspace` с объяснением необходимости расширения границ.

UI проверить отдельно: автоматический debounce/cooldown, оба ручных режима,
смена вопроса во время запроса, ошибка сети, роль shared, ручная привязка,
история и pause/stop. `npm build` не заменяет эти проверки. Browser с явно
включённым demo/mock может доказать UI, но не реальный захват и Tauri workflow.

Provider probe и физическое интервью в рамках автоматических тестов не запускать.
До заявления о пригодности к живому интервью отдельно измерить задержку от
появления final STT до карточки, частоту повторов и полезность на конкретном
provider/model. Целевой ориентир для пилота — полезная карточка в пределах
10 секунд после стабилизации распознанного ответа; это пока не подтверждённый SLA.

Готовность функции: доступны auto + ручной запуск, вопросы проверяемо привязаны
к ответу и rubric, помощь прозрачно отражена в review/отчёте, стоимость ограничена,
STT не блокируется, а revisions, человеческие решения и финальные снимки сохраняют
свои гарантии.
