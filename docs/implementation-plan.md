# Nebula: план реализации

Статус: план к реализации, код приложения пока отсутствует. Основание —
[концепция продукта](product-concept.md). Дата: 9 сентября 2026.

**AI-провайдеры предоставляют OpenAI-совместимые API, но используются не GPT-модели.**
Совместимость протокола и качество конкретной модели проверяются отдельно.
Ни один этап не должен требовать GPT, OpenAI Realtime или другого специфичного
для OpenAI сервиса.

## 1. Результат первой версии и границы

Рабочий сценарий: утверждённый план интервью → явный запуск записи двух каналов →
транскрипция → вопросы и ответы → предварительные оценки → ручная проверка →
детерминированный итоговый балл → подтверждённое резюме → экспорт.

В MVP включаем удалённое интервью одного интервьюера с одним кандидатом,
Windows и macOS, Linux beta. Вопросы и рубрики пользователь создаёт вручную;
генерация вопросов остаётся после MVP, как указано в разделе границ концепции.
Первый язык для проверки — русский с английскими техническими терминами;
поддержку других языков подтверждаем отдельными наборами записей.

За пределами MVP: очный режим, голосовые эталоны, несколько интервьюеров,
ATS/календари, RAG, автономные решения о найме и локальный AI на устройстве.
Потеря сети допускает продолжение записи, но не обещает offline-оценивание.

## 2. Решения до начала основной разработки

| Решение | Предлагаемая исходная точка | Когда закрыть |
| --- | --- | --- |
| Desktop | Tauri 2 + React/TypeScript; нативный аудиослой Rust | После audio spike |
| Backend | Python + FastAPI, HTTP/WebSocket, отдельный worker из того же кодового проекта | Этап 0 |
| Развёртывание | Один управляемый backend для пилота, с рабочими пространствами и разграничением доступа | Этап 0 |
| Данные | PostgreSQL, S3-совместимое хранилище разрешённых аудиоданных; SQLite на desktop | Этап 0 |
| LLM | Один основной OpenAI-compatible провайдер; второй для проверки переносимости | Этап 0–2 |
| STT | Отдельно выбранный сервис распознавания, с live- и batch-возможностями | Этап 0–2 |
| Ограничение API | Уточнить, распространяется ли OpenAI-совместимость также на STT | Этап 0 |
| Поддержка устройств | Зафиксировать версии ОС, архитектуры CPU, гарнитуры и приложения звонков | Этап 1 |
| Лимиты пилота | Длительность интервью, одновременные сессии, допустимые задержки и стоимость | Этап 0 |
| Хранение | Сроки отдельно для временного аудио, архива, транскриптов, отчётов и резервных копий | До записи реальных интервью |
| Доступ | Интервьюер работает со своими интервью; администратор управляет пользователями и политиками | До пилота |

Это предложения для планирования, а не уже принятые решения или реализованные
возможности. Конкретные провайдеры, ID моделей, тарифы и нагрузка пока неизвестны.
Выбор моделей делается по результатам проверки, а не по названию семейства.

## 3. Архитектура без лишних сервисов

```text
Desktop: React UI
    ↕ ограниченные Tauri-команды
Rust: AudioCaptureService → зашифрованный spool + SQLite-индекс → uploader
    ↕ HTTPS / WebSocket, авторизация, ACK и восстановление соединения
Backend API → PostgreSQL + аудиохранилище
    ↕ сохраняемые задания
Worker: STT → turn assembler → question/answer → assessment → summary
    ↕
STT adapter / OpenAI-compatible LLM adapter
```

Начинаем с модульного backend и одного типа worker-процесса. У каждого этапа
конвейера свой модуль и контракт, но не отдельный микросервис. Очередь первого
пилота — таблица заданий PostgreSQL с lease, повторными попытками и дедупликацией;
отдельный брокер добавляется только при измеренной необходимости. Создание
доменных изменений и связанных заданий выполняется в одной транзакции.

Предлагаемая структура репозитория:

```text
apps/desktop/                 # UI и Tauri, включая реализации аудио по ОС
backend/                     # API, доменная логика, worker, adapters, migrations
contracts/                   # JSON Schema, события, примеры протокола
evals/                       # обезличенные/синтетические примеры и отчёты качества
infra/                       # локальный запуск и конфигурация развёртывания
docs/                        # решения, протоколы, матрица проверок
```

Источник истины для подтверждённых данных — backend. SQLite хранит локальный
индекс записи, неподтверждённые отправки и необходимые данные текущего интервью.
Секреты AI-провайдеров остаются на backend; токен сессии desktop и ключи
шифрования защищаются системным хранилищем секретов.

## 4. Контракт с OpenAI-совместимыми провайдерами

### 4.1. Минимальная интеграция

Основной LLM endpoint — `POST /v1/chat/completions`. Адаптер получает профиль
провайдера, точный upstream `model_id`, сообщения и схему результата. На первом
этапе достаточно обычных завершённых ответов: live-интервью не требует стримить
каждый токен LLM. Потоковый STT — отдельная функция.

Один общий адаптер выполняет HTTP-запрос и нормализует ответ. Небольшие настройки
конкретного провайдера добавляются только для обнаруженных различий. Не нужны
агентный framework, tool calling или автоматическая цепочка разных моделей.

Совместимость нельзя считать полной по одному названию API: например, Ollama
прямо описывает поддержку частей OpenAI API. Поэтому список моделей — только
источник ID, а не доказательство возможностей. См.
[документацию совместимости Ollama](https://docs.ollama.com/api/openai-compatibility).

### 4.2. Конфигурация

| Объект | Обязательные данные |
| --- | --- |
| ProviderProfile | Внутренний ID, base URL, ссылка на секрет, допустимые endpoints, таймауты, лимиты параллельности |
| ModelProfile | Provider ID, точный upstream model ID, проверенные возможности, размер контекста/вывода, параметры генерации |
| TaskRoute | Задача → профиль модели, версия prompt, версия схемы, бюджет запроса |
| STTProfile | Endpoint/protocol, модель, языки, форматы аудио, ограничения длительности, timestamps, live/batch |

Маршруты LLM: `question_extraction`, `answer_assessment`, `final_summary`.
Изначально они могут ссылаться на одну модель. Более быструю модель для выделения
вопросов и более сильную для оценивания вводим по измерениям.

`provider_id` и `model_id` — разные поля; исходное имя модели не меняем и не
маскируем под GPT. Настройки не предполагают конкретный tokenizer, размер окна,
наличие `seed`, `temperature`, `max_tokens` либо `max_completion_tokens`.
Каждый параметр включается только для проверенного профиля. Reasoning-режим
отдельно влияет на лимит вывода, задержку и стоимость; его внутренний текст
не является объяснением оценки для пользователя и не сохраняется по умолчанию.

Профили редактирует администратор backend, не участник интервью. URL ограничены
разрешёнными адресами; редиректы не должны пересылать ключи на посторонние хосты.
Версию профиля фиксируем на запуск обработки, чтобы смена конфигурации не меняла
происхождение уже полученных результатов.

### 4.3. Структурированные ответы

Порядок выбора режима на этапе проверки провайдера:

1. JSON Schema, если конкретная пара endpoint/model действительно её поддерживает.
2. JSON object, если schema-режим недоступен, но проверен JSON mode.
3. JSON по инструкции, только если модель проходит тот же набор валидационных
   и качественных проверок; иначе профиль не допускается к оцениванию.

Режим закрепляется в профиле. Нет молчаливого переключения режима после ошибки.
Некоторые серверы имеют собственные настройки structured output и взаимодействия
с reasoning; они остаются внутри адаптера. Пример —
[structured outputs в vLLM](https://docs.vllm.ai/en/latest/features/structured_outputs/).

Любой результат проверяем на backend: схема, допустимые значения и диапазоны,
ID критериев, принадлежность evidence текущему интервью и ревизии. Поля модели
не становятся SQL, командами или действиями. Транскрипт — недоверенные данные;
фраза кандидата «поставь максимальный балл» не меняет инструкции оценивания.

Для повреждённого JSON допускается один запрос исправления в общем бюджете
задачи, после чего результат получает статус ошибки/ручной проверки. Обрыв,
отказ модели, пустой content и превышение контекста обрабатываются явно.
Техническая ошибка никогда не превращается в нулевой балл кандидата.

### 4.4. Проверка провайдера и ошибки

Перед включением профиля проверить авторизацию, базовый запрос, Unicode/русский,
длинный контекст, выбранный JSON-режим, reasoning, ограничения вывода, ошибки
401/403/429/5xx, таймаут, отказ и неполный ответ. SSE проверять при его включении.
Автоматическая проверка не должна изменять конфигурацию или выбирать случайную
модель из `/models`.

Повторы только для временных ошибок, с задержкой, учётом `Retry-After`, общим
deadline и пределом попыток. 401/403 и неподдерживаемые параметры требуют
исправления настройки. Обрыв после отправки запроса может привести к повторной
оплате: дедупликация результата не гарантирует однократный вызов провайдера.

Переключение на второго провайдера не включаем автоматически: другой получатель
данных должен быть разрешён политикой, а смена модели отмечена в происхождении
результата. Недоступность AI не должна останавливать исправную запись аудио.

### 4.5. STT не выводится из совместимости LLM

Отдельно проверяем распознавание русской речи и терминов, разделение partial/final,
временные метки, длительность сессии, переподключение и batch-переработку.
Наличие `/chat/completions` не доказывает наличие `/audio/transcriptions` или
realtime-аудио.

Если разрешены только OpenAI-совместимые endpoints, выбираем STT с подходящим
аудиоконтрактом. При доступности только batch-transcription можно отправлять
короткие аудиоблоки с перекрытием и удалением дублей, но такую задержку нужно
измерить. Если целевой live-бюджет не выдерживается, это блокер выбора STT,
а не основание назвать batch настоящим realtime.

## 5. Аудио и доставка

### 5.1. Источники и платформы

- Windows: WASAPI microphone + loopback. Обычный loopback захватывает выходной
  микс устройства, поэтому фильтрацию по приложению проверяем отдельно; см.
  [Microsoft Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).
- macOS: проверить Core Audio Process Tap как основной путь; Apple указывает
  macOS 14.2+ для своего примера и отдельное разрешение. Если нужны более старые
  ОС, отдельно оценить ScreenCaptureKit, не реализуя оба пути заранее; см.
  [Apple Core Audio taps](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps).
- Linux beta: PipeWire; PulseAudio fallback только для заявленной и проверенной
  матрицы окружений. Поведение в разных desktop environment проверить на стенде.

«Системный канал = кандидат» верно только для звонка один на один без посторонних
источников. Пользователь выбирает приложение/выход, видит два индикатора уровня
и проверяет каналы до старта. Если доступен только общий микс, UI явно сообщает
его границы. Гарнитура — основной режим пилота. Автоматическое разделение
нескольких голосов и удаление эха не являются скрытыми зависимостями MVP.

### 5.2. Формат и устойчивость

- Нативный захват сохраняет метки источника и счётчики сэмплов. Нормализация
  sample rate/каналов выполняется вне realtime callback; финальный формат
  выбирается по требованиям STT и замерам качества/трафика.
- Оба канала привязываются к общей монотонной шкале времени интервью. Измеряем
  начальное смещение и drift, сохраняем сведения о коррекциях и разрывах.
- Chunk содержит `interview_id`, `track_id`, `capture_epoch`, `sequence`,
  временной диапазон, формат, число сэмплов и checksum. Новый epoch отличает
  возобновлённую запись от старой последовательности.
- Сначала атомарно сохраняем зашифрованный chunk и индекс, затем отправляем.
  Backend подтверждает только устойчиво сохранённый chunk. Повтор того же ID
  не создаёт копию; тот же ID с другим checksum — конфликт.
- Переподключение сверяет сохранённые последовательности/пропуски. Сетевой ACK
  доставки не означает завершение STT и не разрешает удалить единственную
  копию, нужную для финального прохода.
- Ограничиваем RAM, размер дискового буфера и backlog. При нехватке места
  показываем проблему и останавливаем/приостанавливаем запись с отметкой разрыва,
  не удаляя незаметно неотправленные данные.
- После падения приложения предлагаем восстановить запись и отправку уже
  сохранённого; автоматически начинать новую запись нельзя. Sleep/resume,
  смена устройства и отзыв разрешений отражаются в состоянии каналов.
- Pause прекращает захват новых данных; уже записанные блоки могут догружаться.
  Stop закрывает manifest дорожек, после чего финализация ждёт загрузку либо
  явное признание неполной записи. Пропущенные интервалы видны пользователю.

## 6. Доменная модель и ревизии

| Сущность | Что фиксируем |
| --- | --- |
| Interview | Владелец/workspace, минимальные данные кандидата, роль, язык, состояние, согласие и политика хранения |
| InterviewPlan / RubricRevision | Вопросы, критерии, шкалы, допустимые альтернативы, веса; утверждённая неизменяемая версия |
| AudioTrack / AudioChunk | Источник, временная шкала, manifest, integrity, пропуски, размещение и срок удаления |
| TranscriptRevision / Segment | Stable ID, версия, track, timestamps, текст, partial/final, качество при наличии, происхождение |
| Question / AnswerLink | Запланированный или новый вопрос, уточнения, связи с диапазонами сегментов, ручные корректировки |
| AssessmentProposal | Баллы/отсутствие балла, критерии, объяснение, evidence, причина review, версии всех входов |
| HumanAssessment | Подтверждённые/изменённые человеком значения, автор, время, основание изменения |
| ReportRevision | Снимок подтверждённых входов, формула и балл, покрытие, summary, подтверждение рекомендации |
| ProcessingRun / Job | Этап, версии входов, профиль модели, prompt/schema, попытки, состояние, usage, ошибка |
| AuditEvent | Автор/система, действие, объект и ревизии, время; без дублирования транскрипта в техлоге |

Жизненный цикл интервью: `draft → ready → recording ↔ paused → processing →
review → finalized`. Состояние записи, загрузки и отдельных заданий учитывается
отдельно: ошибка AI не делает интервью потерянным. Состояние удаления запрещает
новые задания и принятие поздних результатов.

Главные правила согласованности:

1. Partial-текст предназначен для UI. В оценивание попадают только завершённые
   сегменты, а результаты ссылаются на конкретную ревизию входов.
2. Финальный STT не перезаписывает ручные правки. Создаёт предлагаемую ревизию,
   сопоставление старых/новых сегментов и видимые расхождения; неразрешимые связи
   evidence требуют ручной проверки.
3. Изменение текста, связи ответа, рубрики или оценки помечает зависимые
   предложения/отчёты устаревшими. Человеческое подтверждение нельзя автоматически
   перенести на изменившийся смысловой источник.
4. Ответ старого фонового задания сохраняется как исторический либо отклоняется,
   но не подменяет новую версию. Обновления клиента используют expected revision
   и получают конфликт при устаревшем состоянии.
5. Итоговый отчёт — подтверждённый снимок. Последующая правка создаёт новую
   ревизию с повторным подтверждением; ранее выданный экспорт не меняется.

## 7. Вопросы, ответы, оценки и итог

### 7.1. Сборка интервью

LLM классифицирует завершённые реплики интервьюера и предлагает границы вопросов,
уточнений и ссылки на утверждённый план. State machine хранит текущий вопрос,
уточнения, накопленный ответ и статус его завершения. Пауза сама по себе не
доказывает, что ответ окончен: закрытие учитывает следующий вопрос, явное действие
интервьюера или проверенное правило таймаута с возможностью продолжения.

Нужны сценарии: перебивание, ответ после паузы, повтор вопроса, возврат к старому
вопросу, несколько вопросов в реплике, встречный вопрос кандидата, small talk,
ответ до формулировки вопроса и пропущенный аудиофрагмент. При неоднозначности
сохраняем несвязанный фрагмент и предлагаем ручную привязку. В UI доступны
разделение/объединение вопросов и перенос сегментов ответа.

Новый вопрос без утверждённой рубрики записывается, но не получает числовой
AI-оценки до добавления и утверждения рубрики человеком.

### 7.2. Оценивание

На вход: утверждённая рубрика, вопрос и уточнения, релевантные сегменты ответа,
предупреждения о качестве, версии. Весь часовой транскрипт в каждый запрос не
отправляется. Для длинных ответов выделение evidence выполняется по частям
с сохранением ссылок; нельзя незаметно обрезать хвост или заменить исходные
доказательства одним модельным пересказом.

На выход: баллы по критериям или `null`, краткое объяснение, evidence с ID/версией
и диапазоном текста, пропуски, критические ошибки, допустимые альтернативы,
причины ручной проверки. Ссылки валидируются программно; смысловую обоснованность
проверяют evals и интервьюер. Одного существующего ID недостаточно для доверия.

Уверенность модели — заявленная самооценка, не вероятность правильности.
До калибровки не показываем ложную точность вроде «94% достоверности».
Отдельно показываем наблюдаемые проблемы: пропуск канала, неполный ответ,
невалидный результат, конфликт evidence. «Не прозвучало» не означает «не знает».

В наборе проверок должны быть инструкции внутри ответа, слабая транскрипция,
нестандартное корректное решение, многословный неверный ответ и изменения
личных характеристик при неизменном профессиональном содержании.

Рубрики и основания ограничены профессиональным содержанием: акцент, тембр,
скорость речи, предполагаемые эмоции, пол, возраст и другие личные или защищённые
признаки не используются для оценки. Аудиопризнаки качества нужны для диагностики
транскрипции, а не для выводов о кандидате. Выявленное недопустимое основание
блокирует утверждение предложения до исправления; одного запрета в prompt
недостаточно, нужны проверки рубрик, примеров и ручной review.

### 7.3. Человеческая проверка и балл

AI-предложение и человеческая оценка хранятся раздельно. Интервьюер подтверждает
или меняет критерии, видит источники и отмечает недостаток данных. Пропущенный
вопрос не равен нулю; ноль допустим только по рубрике и с подтверждением человека.

Предлагаемая формула: каждый подтверждённый критерий нормализуется в `[0, 1]`
по своей шкале; балл вопроса — среднее по весам критериев; итог — среднее по весам
вопросов, умноженное на 100. Проверяем непустые диапазоны шкал, неотрицательные
веса и положительную сумму весов. Округление — только при отображении.

Неразрешённые обязательные критерии блокируют финализацию. Явное исключение
вопроса/критерия человеком требует причины и обновляет знаменатель; рядом с
итогом показываем покрытие по исходным весам, чтобы исключения не скрывали
неполноту интервью. При пустом наборе итог отсутствует. Критические ошибки
выводятся явно; автоматический отказ или скрытый штраф не вводится.

Summary получает только актуальные подтверждённые данные и необходимые источники,
возвращает тезисы с evidence. Числовые результаты подставляет backend. Интервьюер
проверяет и подтверждает текст и рекомендацию; отсутствие оснований отражается
как ограничение, а не заполняется предположением модели.

## 8. Экраны и API

Минимальные экраны: список интервью; редактор плана/рубрик; проверка звука и
согласия; запись с двумя уровнями каналов, транскрипцией и вопросами; обработка
и восстановление; ручной review; отчёт/экспорт; настройки подключения и хранения.
Ошибки показываются рядом с затронутой функцией и сохраняют доступ к тексту.

Backend-контракт покрывает создание/утверждение плана, начало/паузу/завершение
сессии, загрузку chunk и сверку manifest, поток событий, редактирование с revision,
подтверждение оценок, финализацию, экспорт и удаление. События имеют `event_id`,
версию схемы и cursor для восстановления; после потери истории клиент получает
актуальный snapshot. Команды начала/завершения и фоновые задания идемпотентны.

Экспорт MVP: JSON для структурированных данных и PDF для чтения. Включить рубрики,
подтверждённые оценки, покрытие, основания, ограничения записи, автора/дату и
ревизию отчёта. Экспорт черновика помечается явно. Секреты и внутренние рассуждения
модели в экспорт не попадают; вложение аудио — только отдельное явное действие.

## 9. Приватность и безопасность в реализации

- До захвата фиксируем явное подтверждение согласия участников, его время и
  версию текста; индикатор записи и Pause/Stop доступны постоянно. Точный процесс
  получения согласия и требования региона утверждаются до пилота.
- Согласие фиксируется по участникам, включая способ подтверждения и отзыв.
  Без необходимого согласия нельзя начать захват и загрузку. При отзыве
  прекращаем новый захват/передачу и блокируем дальнейшие AI-задания; судьба уже
  собранных данных определяется заранее утверждённой политикой, с видимым
  состоянием удаления или ограничения обработки.
- Различаем временную обработку аудио и архив после интервью. Финальная
  повторная транскрипция требует доступных исходных дорожек. Если запрещено
  даже временное сохранение, этот сценарий концепции невыполним без изменения
  режима: повторный проход недоступен, что должно быть явно показано.
- HTTPS/WSS; шифрование аудио и содержащих текст локальных данных, включая
  SQLite WAL/временные файлы. На сервере защищаем БД, объекты и резервные копии;
  ключи не храним рядом с данными в открытом виде и не изобретаем свой криптоформат.
- Временный локальный оригинал сохраняем до успешной финальной обработки в
  пределах согласованного TTL. При истечении TTL задача становится недоступной
  или неполной; срок нельзя бесшумно продлевать ради повторной обработки.
- Авторизация применяется к каждому интервью, chunk, событию, заданию и экспорту.
  Signed URL короткоживущие; администратор настройки не получает автоматически
  неограниченный доступ к содержимому всех интервью.
- Удаление отменяет задания, запрещает поздние записи результатов и очищает БД,
  объекты, локальный cache при следующей синхронизации и временные экспорты.
  Недоступный desktop и backup имеют отдельные сроки очистки; удаление нельзя
  объявлять мгновенным для всех копий. Скачанные пользователем файлы не отзываются.
- Аудит хранит минимальные метаданные; содержательные версии имеют собственный
  срок хранения и удаляются согласно политике. Audit log не должен становиться
  бессрочной копией удалённого интервью.
- Проверяем условия выбранных STT/LLM-провайдеров: хранение, использование данных,
  регионы, субпровайдеры. Только разрешённые получатели участвуют в маршрутизации.
- Логи и трассировки по умолчанию без аудио, транскриптов, prompt, токенов и ключей.
  Tauri-команды получают минимальные разрешения, внешняя страница не должна иметь
  доступ к нативным API; см. [Tauri capabilities](https://v2.tauri.app/security/capabilities/).

## 10. Этапы, зависимости и критерии приёмки

Все этапы ниже пока **не начаты**. Завершение означает проверенный результат,
а не только наличие реализации или успешную сборку.

| Этап | Работа и результат | Условие перехода |
| --- | --- | --- |
| 0. Контракты и ограничения | Зафиксировать решения раздела 2, сценарии, схемы данных и провайдерские профили; подготовить разрешённые тестовые записи и рубрики | Нет неизвестного, мешающего audio/STT spike; определены лимиты и матрица пилота |
| 1. Audio spike | Минимальная диагностическая оболочка на трёх ОС, два канала, timestamps, шифрованный spool, replay, разрешения | Часовые реальные записи на Windows/macOS проходят матрицу отказов; Linux получает честный beta-статус; выбран desktop-стек |
| 2. AI/STT spike | Проверить STT и минимум две пары provider/model без GPT; схемы, качество, стоимость и задержки | Основной набор проходит согласованные пороги; замена LLM-провайдера выполняется конфигурацией без изменения домена |
| 3. Основа приложения | Репозиторий, CI, API/worker, миграции, авторизация, хранение, durable jobs, аудит и desktop shell | Создание интервью, сохранение плана, безопасное подключение, загрузка/replay и восстановление работают сквозным сценарием |
| 4. Вертикальный срез | Один утверждённый вопрос: запись → STT → ответ → оценка → review → итог → экспорт | Полный сценарий проходит на реальном звонке; по каждому баллу можно открыть подтверждающий текст |
| 5. Полное live-интервью | Несколько вопросов, уточнения, state machine, ручная привязка, деградация каналов/AI | Размеченные сценарии перебиваний/возвратов воспроизводятся, неоднозначность не скрывается |
| 6. Финальный контур | Batch-STT, ревизии, конфликты правок, пересчёт предложений, подтверждённый summary и экспорт | Финальная обработка не уничтожает ручные изменения; устаревшие оценки/отчёты нельзя выдать за актуальные |
| 7. Надёжность и пилот | Fault injection, нагрузка, privacy lifecycle, резервирование/восстановление, подписанные установщики, обновление | Пройдены выпускные проверки; проведён ограниченный пилот с ручным разбором расхождений |

Зависимости: `0 → (1 и 2) → 3 → 4 → 5 → 6 → 7`.
Этапы 1 и 2 независимы и могут выполняться параллельно. Защита данных начинается
на этапе 3, до использования реальных данных, а на этапе 7 проверяется целиком.
В вертикальный срез включается простой итог; полноценное сравнение live/final
и жизненный цикл пересмотров завершаются на этапе 6.

## 11. Проверки и измеримые пороги

Числа ниже — **стартовые цели пилота**, не гарантии и не измеренные результаты.
Уточняем их после этапов 1–2 и фиксируем до приёмки вертикального среза.

| Область | Проверка/цель |
| --- | --- |
| Аудио | 60 минут на каждой основной ОС; рассинхронизация каналов ≤ 200 мс; нет незамеченных пропусков |
| Offline-буфер | 10 минут без сети, reconnect и перезапуск процесса; сохранённые chunks восстанавливаются без дублирования |
| Live-STT | p95 ≤ 3 с от конца речевого блока до завершённого текста при штатной сети |
| Предложение оценки | p95 ≤ 10 с от закрытия ответа до валидного результата; backlog виден |
| Final | Час интервью обрабатывается ≤ 15 минут при согласованной нагрузке и доступных исходниках |
| Формат LLM | ≥ 99% ответов проходят схему с максимум одним исправлением; невалидные результаты никогда не публикуются как оценки |
| Вопросы/связи | Precision/recall/F1 на размеченных интервью; стартовая цель F1 ≥ 0,90, неоднозначные связи учитываются отдельно |
| Содержание оценок | На стартовом наборе 100 ответов с экспертной разметкой ≥ 90% оценок в пределах одного уровня согласованной пятиуровневой рубрики; критические неподтверждённые выводы блокируют допуск |
| Целостность | Повтор событий/заданий и поздние ответы не меняют подтверждённые ревизии; ссылки evidence всегда относятся к своим входам |
| Доступ/удаление | Другой пользователь/workspace не читает интервью; удаление не допускает восстановления содержимого поздним worker |

Качество STT измеряем WER/CER и отдельно сохранность терминов, отрицаний и чисел.
Общий WER не заменяет разбор ошибок, влияющих на оценку. Учитываем расхождения
самих экспертов; небольшой стартовый набор не доказывает качество во всех ролях.
Храним отдельную выборку, не использовавшуюся при настройке prompt.

Необходимые автоматические проверки: формула и исключения; state machine;
валидация/evidence; инвалидация ревизий; миграции; авторизация; идемпотентность;
срыв и восстановление заданий; контракты provider/STT на фиксированных fixtures.
Реальные вызовы моделей — отдельные управляемые eval-запуски с лимитом расходов.

Необходимые проверки на устройствах: USB/Bluetooth и смена default device,
тишина/клиппинг/эхо, смешанные источники, отключение канала, отзыв разрешений,
sleep/resume, закрытие приложения звонка, переполнение диска, обрыв сети и crash.
Сборка в CI не заменяет эти проверки, включая тестирование подписанного пакета.

## 12. Стоимость, наблюдаемость и выпуск

Для каждого этапа измеряем очередь, время обработки, retries, ошибки, usage и
приблизительную стоимость без содержимого интервью. Если провайдер не возвращает
usage, стоимость помечается как оценка/неизвестная, а не как ноль.

Стоимость интервью складывается из STT по обоим каналам и обоим проходам,
LLM input/output с повторными запросами, хранения, трафика и сервера. Финальный
проход и повторы могут заметно увеличить бюджет. Модельный tokenizer используем
при доступности; иначе резервируем консервативный контекстный бюджет и обрабатываем
отказ по длине. Не подставляем GPT-tokenizer как универсальный.

Лимиты: длительность сессии, дисковый spool, размер входа/вывода, число запросов
и параллельных задач на пользователя/workspace. Сначала масштабируем по замерам;
смена модели ради цены допускается после повторного eval и фиксируется в отчёте.

Выпуск: миграции с проверенным восстановлением, секреты вне репозитория, backup
и restore, health/readiness, подписанные Windows-сборки, подпись/notarization
macOS, проверенные Linux-пакеты. Обновления подписываются и устанавливаются
вне активной записи; изменения клиентского протокола и БД имеют проверенный
путь совместимости. До пилота нужны инструкции диагностики и восстановления.

Календарный срок сейчас был бы предположением: неизвестны команда, платформенные
стенды, провайдеры и качество STT. После этапов 1–2 оценить трудоёмкость этапов
3–7 по фактически выбранным API и найденным проблемам. Критический путь проходит
через аудио, STT и корректную работу ревизий, а не через оформление экранов.

## 13. Первые задачи в backlog

1. Зафиксировать минимальные версии ОС, приложения звонков, языки, нагрузку,
   ограничения хранения и кандидатов в LLM/STT-провайдеры.
2. Подготовить диагностическую двухканальную запись и протокол часового теста.
3. Подготовить минимальный provider probe: completion → schema → evidence,
   с точными ID моделей не GPT и проверкой несовместимых параметров.
4. Запустить STT-пробу на одинаковых двухканальных записях: live и final,
   timestamps, термины, задержка и стоимость.
5. По результатам утвердить стек и профили, затем собрать один вертикальный
   сценарий, прежде чем расширять UI и количество вопросов.

Документация API в ссылках проверена при составлении плана. Эти источники
обосновывают технические ограничения, но не являются выбором конкретного
провайдера для Nebula; совместимость реальных профилей ещё нужно измерить.
