## Назначение

Nebula связывает разговор, аудиозапись, транскрипцию, анализ ответов и итоговый отчёт в одну проверяемую цепочку. Система предназначена для технических и профессиональных интервью.

Nebula — это decision-support, а не автономный судья:

- AI формирует предварительные предложения, а решение принимает интервьюер.
- У каждой оценки должны быть проверяемые фрагменты речи кандидата.
- Итоговый балл считается обычным кодом по подтверждённым человеком данным.
- Ручные правки, решения и история изменений не перезаписываются AI.
- Оценивается содержание ответа по профессиональной рубрике, а не акцент, тембр, скорость речи, пол, возраст или другие личные признаки.

## Пользовательский сценарий

### До интервью

1. Интервьюер создаёт интервью, указывает роль, уровень и компетенции.
2. Добавляет вопросы и для каждого задаёт критерии, шкалу, вес, ожидаемые элементы и критические ошибки.
3. Проверяет план и явно подтверждает готовность к записи.

### Во время интервью

1. Пользователь явно запускает запись и видит состояние обоих аудиоканалов.
2. Nebula захватывает микрофон интервьюера и звук кандидата отдельными дорожками.
3. Система показывает live-транскрипцию, выделяет вопросы и связывает ответы с открытым вопросом.
4. После завершения ответа AI предлагает предварительную оценку, объяснение, уверенность и ссылки на фрагменты транскрипта.

### После интервью

1. Выполняется финальная обработка исходных дорожек.
2. Интервьюер проверяет транскрипцию, связи «вопрос — ответ» и оценки.
3. Backend рассчитывает итоговый балл и покрытие по подтверждённым значениям.
4. AI формирует доказательное резюме, сильные стороны и пробелы только по актуальным подтверждённым данным.
5. Интервьюер подтверждает рекомендацию и экспортирует отчёт.

## Аудиозахват

### Каналы и платформы

Основной сценарий — удалённое интервью одного интервьюера с одним кандидатом:

- `interviewer` — микрофон интервьюера;
- `candidate` — системный звук приложения звонка через loopback или виртуальное устройство.

Поддерживаемые направления: Windows — WASAPI microphone/loopback, macOS — Core Audio Process Tap или согласованный альтернативный путь, Linux — PipeWire с PulseAudio fallback.

Системный канал можно считать голосом кандидата только для звонка один на один без посторонних источников. Перед стартом пользователь выбирает устройство/приложение и проверяет уровни. Гарнитура рекомендуется для удалённых интервью.

### Реализация записи

- Realtime-аудиоколлбек не выполняет аллокации, файловый ввод-вывод и блокирующие mutex-операции.
- Сэмплы передаются через lock-free ring buffer в фоновый поток.
- Фоновый поток сводит каналы в mono, ресемплирует до `16 000 Hz PCM_S16LE` и режет поток на чанки, по умолчанию по 2 секунды.
- Каналы привязаны к общей монотонной шкале времени; сохраняются смещение, drift, разрывы и коррекции.
- Чанк содержит `interview_id`, `track_id`, `capture_epoch`, `sequence`, временной диапазон, формат, число сэмплов и `SHA-256`.

Дрейф и рассинхронизация считаются так:

```text
Drift(track) = samples × 1000 / sample_rate − elapsed_wall_ms
Skew = Drift(candidate) − Drift(interviewer)
```

Критерий качества для 60 минут записи — `|Skew| ≤ 200 мс`.

### Локальный spool и восстановление

```text
spool/<interview_id>/<track_id>/
├── 00000000.chunk
├── 00000000.meta.json
└── manifest.json
```

Каждый чанк сначала записывается во временный файл, синхронизируется и атомарно переименовывается в `.chunk`. Проверка spool пересчитывает SHA-256 и обнаруживает повреждения и пропуски последовательности. Повторная отправка того же идентификатора идемпотентна; тот же идентификатор с другим checksum является конфликтом.

При обрыве сети или падении приложения сохранённые чанки не удаляются. После восстановления система сверяет последовательности и продолжает загрузку. При нехватке диска запись явно приостанавливается с отметкой разрыва. После `Stop` manifest закрывается только после подтверждения backend либо явно помечается неполным.

Диагностические команды:

```bash
cargo run -p audio-spike -- list-devices
cargo run -p audio-spike -- synthetic-test --simulated-duration-sec 3600
cargo run -p audio-spike -- record --duration-sec 5 --output-dir ./spool/test_run
cargo run -p audio-spike -- verify-spool ./spool/test_run --interview-id spike-session
```

## AI-конвейер и провайдеры

Конвейер разделён на независимые этапы:

```text
STT → сборщик реплик → вопрос/ответ → assessment → summary
```

Есть два контура:

- **Live:** потоковая или короткими блоками транскрипция, выделение вопросов и предварительная оценка после завершения реплики.
- **Final:** повторная транскрипция исходных дорожек, уточнение временных границ, восстановление связей, пересчёт предложений и summary после ручной проверки.

### Контракт провайдера

LLM подключается через OpenAI-compatible `POST /v1/chat/completions`, но совместимость протокола не означает наличие GPT, STT, JSON Schema или reasoning. STT проверяется отдельно через подходящий аудиоэндпойнт; наличие `/chat/completions` не доказывает наличие `/audio/transcriptions`.

Профиль провайдера хранит base URL, разрешённые endpoints, таймауты и лимиты. Профиль модели хранит точный upstream `model_id`, проверенные возможности, формат structured output, лимиты контекста/вывода и capability отключения reasoning. `provider_id` и `model_id` не смешиваются и не маскируются под GPT.

Порядок выбора структурированного ответа:

1. `json_schema`, если он проверен для конкретной пары provider/model;
2. `json_object`, если schema-режим недоступен, но JSON mode проверен;
3. JSON по инструкции — только после тех же проверок качества и валидации.

Молчаливое переключение режима после ошибки запрещено. Ответ проверяется на схему, диапазоны, идентификаторы критериев, принадлежность evidence текущему интервью и ревизии. Повреждённый JSON можно один раз запросить повторно в рамках общего бюджета задачи; затем создаётся ошибка или ручная проверка. Ошибка AI никогда не превращается в нулевой балл и не останавливает исправную запись.

Повторы разрешены только для временных ошибок (`429`, `500`, `502`, `503`, `504`) с backoff, `Retry-After`, deadline и ограничением числа попыток. Ошибки `401/403`, неподдерживаемые параметры и неверный JSON требуют исправления настройки. Автоматическое переключение на другого провайдера не выполняется без разрешённой политики.

### STT и LLM-настройки

STT и LLM настраиваются независимо через Desktop и REST API. Конкретные модели, тарифы и параметры должны подтверждаться probe для точной пары provider/model; они не считаются доказанными по названию API.

- Несекретные настройки хранятся в SQLite (`ai_settings`).
- API-ключи не сохраняются в БД, не логируются и не возвращаются клиенту; они записываются в защищённый versioned-файл с правами `0600` на Unix.
- Переменные `NEBULA_STT_API_KEY` и `NEBULA_LLM_API_KEY` имеют приоритет над настройками UI.
- Действия с ключом: `preserve`, `replace`, `clear`; ключ нельзя молча перенести на другой origin.
- `PUT /api/v1/settings/ai` использует `expected_revision` и возвращает `409 Conflict` при конфликте.
- Настройки нельзя менять во время записи/паузы или при активных заданиях `PENDING/PROCESSING`.
- Worker перечитывает ревизию и пересобирает immutable `WorkerAiBundle` без перезапуска процесса; лимиты STT и LLM разделены.

Основные endpoint настройки: `GET /api/v1/settings/ai`, `PUT /api/v1/settings/ai`, `POST /api/v1/settings/ai/test`, `GET /api/v1/system/models`. Тест подключения не сохраняет неподтверждённую конфигурацию и не возвращает секрет.

Для проверки провайдера:

```bash
uv run python evals/provider_probe.py
uv run python evals/run_stage2_probe.py
```

Probe должен проверять авторизацию, Unicode/русский, длинный контекст, structured output, reasoning, таймауты, `401/403/429/5xx`, неполный ответ и фактическую валидацию evidence. Не следует автоматически выбирать случайную модель из `/models`.

## Доменная модель и жизненный цикл

Ключевые сущности:

- `Interview` — владелец/workspace, роль, язык, согласие, политика хранения и состояние.
- `InterviewPlan` / `RubricRevision` — утверждённая версия вопросов, критериев, шкал и весов.
- `AudioTrack` / `AudioChunk` — источник, временная шкала, manifest, checksum и пропуски.
- `TranscriptRevision` / `Segment` — стабильный ID, версия, track, timestamps, текст и качество.
- `Question` / `AnswerLink` — вопрос, уточнения и связь с диапазонами сегментов.
- `AssessmentProposal` — предложение AI с баллами, объяснением, evidence, уверенностью и причиной ручной проверки.
- `HumanAssessment` — подтверждение или изменение человеком с автором, временем и основанием.
- `ReportRevision` — снимок подтверждённых входов, формулы, score, coverage и summary.
- `ProcessingRun` / `Job` — этап, версии входов, профиль модели, prompt/schema, попытки, usage и ошибка.
- `AuditEvent` — минимальная история действий без дублирования транскрипта в технических логах.

Жизненный цикл:

```text
DRAFT → READY → RECORDING ↔ PAUSED → PROCESSING → REVIEW → FINALIZED
  ↓       ↓         ↓          ↓          ↓          ↓         ↓
───────────────────────────→ DELETED ←─────────────────────────
```

`DELETED` — терминальное состояние: новые чанки и фоновые результаты отклоняются. `FINALIZED` — неизменяемый снимок отчёта. Любая последующая правка создаёт новую ревизию и требует повторного подтверждения.

Правила ревизий:

- Partial-текст используется для UI; оценивание опирается только на завершённые сегменты.
- Финальный STT создаёт новую предлагаемую ревизию и видимые расхождения, не перезаписывая ручные правки.
- Изменение транскрипта, связи ответа, рубрики или оценки помечает зависимые AI-результаты устаревшими.
- Старый ответ фоновой задачи не подменяет новую версию; клиент использует expected revision и получает конфликт при устаревшем состоянии.

## Скоринг и evidence

Для критерия нормализованный балл:

```text
s_c = (raw_score − min_c) / (max_c − min_c),  s_c ∈ [0, 1]
```

Если `max_c ≤ min_c`, это ошибка конфигурации шкалы. Балл вопроса — взвешенное среднее активных критериев:

```text
S_q = Σ(w_c × s_c) / Σ(w_c)
```

Итоговый балл от 0 до 100:

```text
FinalScore = (Σ(W_q × S_q) / Σ(W_q)) × 100
```

Покрытие интервью:

```text
Coverage = (Σ W_q активных вопросов / Σ W_q запланированных вопросов) × 100%
```

Исключённый человеком или неоценённый критерий убирается из знаменателя вопроса. Пропущенный вопрос не превращается в искусственный ноль, но уменьшает coverage.

Каждое `AssessmentProposal` проходит программную проверку:

1. `segment_id` существует в указанной `TranscriptRevision`.
2. `exact_quote` дословно присутствует в сегменте речи кандидата.
3. Evidence принадлежит текущему интервью и актуальной ревизии.
4. Объяснение не содержит prompt injection и команд вроде «поставь максимальный балл».
5. Объяснение не использует запрещённые нерелевантные признаки.

Реплики интервьюера и `unknown` в режиме `single_source` не используются как evidence кандидата. При недостатке данных система передаёт результат на ручную проверку, а не ставит ноль.

## Интерфейс, API и экспорт

Минимальный пользовательский путь включает экраны: список интервью; редактор плана и рубрик; проверку устройств и согласия; запись с уровнями каналов, транскрипцией и вопросами; обработку и восстановление; ручной review; отчёт/экспорт; настройки провайдеров и хранения.

Backend должен поддерживать создание и утверждение плана, start/pause/stop, загрузку чанков и сверку manifest, поток событий, редактирование с revision, подтверждение оценок, финализацию, экспорт и удаление. События имеют `event_id`, версию схемы и cursor; после потери истории клиент получает актуальный snapshot. Команды и фоновые задания идемпотентны.

Экспорт: JSON для структурированных данных и PDF для чтения. В отчёт входят рубрики, подтверждённые оценки, coverage, основания, ограничения записи, автор, дата и ревизия. Черновик помечается явно; секреты и внутренние рассуждения модели не экспортируются. Аудио вкладывается только отдельным явным действием.

## Приватность и безопасность

- До записи фиксируется явное согласие участников, его время и версия текста.
- Индикатор записи и `Pause/Stop` постоянно доступны.
- Сроки хранения аудио, транскриптов, отчётов, резервных копий и временного spool задаются политикой.
- Поддерживаются отзыв согласия, удаление и экспорт данных; удаление отменяет задания и запрещает поздние результаты.
- Передача выполняется по HTTPS/WSS, локальные и серверные данные шифруются штатными средствами, ключи хранятся отдельно от данных.
- Доступ проверяется для каждого интервью, чанка, события, задания и экспорта.
- Signed URL должны быть короткоживущими; администратор настроек не получает автоматически доступ ко всем интервью.
- Логи и трассировки не содержат аудио, транскриптов, prompt, токенов и ключей.
- Условия хранения и использования данных каждого внешнего STT/LLM-провайдера проверяются до включения профиля.

## Архитектура и структура репозитория

```text
apps/desktop/         # Tauri 2 + React/TypeScript, UI и IPC
apps/audio-spike/     # диагностика аудиоустройств и synthetic-тесты
crates/audio-capture/ # Rust: realtime-захват, ресемплинг, drift и spool
backend/              # FastAPI, доменная логика, worker, adapters, migrations
contracts/            # Pydantic-модели, JSON Schema и события
evals/                # provider probe и синтетические проверки
tests/                # unit, contract, integration и e2e-тесты
docs/                 # исходные проектные материалы
```

Поток данных:

```text
React UI
  ↕ ограниченные Tauri-команды
Rust AudioCaptureService → зашифрованный spool + SQLite-индекс → uploader
  ↕ HTTPS/WebSocket, авторизация, ACK и восстановление
Backend API → PostgreSQL/хранилище аудио → durable jobs
Worker: STT → turns → question/answer → assessment → summary
```

Источник истины для подтверждённых данных — backend. SQLite на desktop хранит локальный индекс, неподтверждённые отправки и данные текущего интервью. Секреты AI-провайдеров остаются вне базы.

## Возможности

Nebula поддерживает удалённые интервью, одного интервьюера и одного кандидата, раздельный захват, live-транскрипцию, выделение вопросов и ответов, предварительные оценки, ручную проверку, детерминированный итог, evidence-summary и экспорт. Автономное решение о найме не используется: итог подтверждает интервьюер.

## Быстрый старт

```bash
uv sync
uv run pytest -q
uv run ruff check .

cargo test --workspace
cargo fmt --all -- --check

npm --prefix apps/desktop ci
npm --prefix apps/desktop run build
```

Для разработки сервисов:

```bash
./scripts/start.sh backend
./scripts/status.sh
./scripts/stop.sh backend
```

Для desktop-режима используются Tauri, разрешения ОС, `.env`, backend/worker и аудиоустройства.

## Сборка и передача релиза

```bash
npm --prefix apps/desktop run tauri build
uv run python scripts/verify_release.py
```

Сборка кладёт `Nebula.app` и `Nebula_<version>_<arch>.dmg` в `target/release/bundle/`.
Проверка монтирует DMG и убеждается, что exec-биты на месте, подпись бандла
валидна, карантина нет, а сайдкар отвечает на `/healthz`. Флаги `--app` и
`--no-launch` позволяют проверить `.app` напрямую и без запуска.

Для передачи используйте DMG: архивы (в частности, zip из мессенджеров) не
сохраняют Unix-права, и после распаковки приложение не запускается.

Подпись — ad-hoc, поэтому на чужой машине macOS заблокирует запуск (нужны
Developer ID и нотаризация). Для локальной проверки карантин снимается
командой `xattr -cr Nebula.app`.

## Контроль качества

Контрольные показатели продукта:

| Область | Цель проверки |
| --- | --- |
| Аудио | 60 минут на основной ОС, рассинхронизация каналов не более 200 мс, без незамеченных пропусков |
| Offline-spool | 10 минут без сети, reconnect и перезапуск процесса без дублей |
| Live STT | p95 не более 3 секунд от конца речевого блока до финального текста |
| Предложение оценки | p95 не более 10 секунд после закрытия ответа |
| Финальная обработка | час интервью не более 15 минут при согласованной нагрузке и доступных исходниках |
| Structured output | не менее 99% ответов проходят схему максимум с одним исправлением; невалидные результаты не публикуются |
| Связи вопросов и ответов | F1 не ниже 0,90 на размеченных интервью |
| Содержание оценок | не менее 90% оценок в пределах одного уровня согласованной пятиуровневой рубрики на экспертной выборке |
| Целостность | повторы и поздние ответы не меняют подтверждённые ревизии; evidence всегда относится к своим входам |
| Доступ и удаление | другой пользователь/workspace не читает интервью; поздний worker не восстанавливает удалённые данные |

Критерии проверяются для аудио, STT, provider/model, доменных контрактов, авторизации, идемпотентности, ревизий и удаления, включая USB/Bluetooth, смену устройства, тишину, клиппинг, эхо, sleep/resume, сетевые сбои и crash recovery.
